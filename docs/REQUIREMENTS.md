## 1. 文档目的

本文档记录“全员逃走中-扩展”模组及其配套数据包目前已经对齐的完整要求，作为后续设计、开发、验收和扩展时的统一依据。

## 2. 项目定位

### 2.1 核心目标

本项目用于制作 Minecraft 版“全员逃走中”的通用运行底座，重点提升：

- 开局前流程的完整性和可控性；
- 玩家与主持人的界面体验；
- 动画、文字、声音、镜头等节目化表现；
- 状态持久化、异常恢复和多人环境可靠性；
- 后续地图、任务和新玩法的复用能力；
- 相比纯数据包更自由、更连贯的客户端表现。

项目不是只服务于当前一张地图。未来“全员逃走中 2.0”或其他变体应尽量通过新游戏配置、数据包及资源包实现，而不是复制并分叉整个模组。

### 2.2 旧项目的使用边界

旧仓库：

- <https://github.com/zcpu954861/1.21.11-tzz_game_datapack>

旧项目只用于帮助理解已有经验、玩法语境和曾经遇到的问题，不复用：

- 旧地图；
- 旧任务；
- 坐标与结构；
- 旧流程；
- 旧代码；
- 为旧项目写死的架构。

本项目是一次独立、从零设计的新实现。

### 2.3 已知但尚未确定的内容

以下内容尚未定案：

- 正式游玩的主线；
- 地图；
- 具体任务；
- 复活任务的规则与内容；
- 最终音效资产；
- 具体游戏结束条件；
- 各游戏配置中的自定义字段；
- 远距离运镜所需区块加载方案的最终选择。

这些内容不得提前写死到模组核心。

## 4. 总体架构

### 4.1 组成

项目采用三层结构：

1. **服务端模组核心**
   - 游戏阶段；
   - 主持人；
   - 玩家身份与自定义数据；
   - 准备状态；
   - 角色；
   - 存活、捕获、复活状态；
   - 权限校验；
   - 持久化；
   - 数据包桥接；
   - 网络请求的最终裁决。

2. **客户端模组表现层**
   - 自定义 GUI；
   - HUD；
   - 动态聊天文本；
   - 动画与音效；
   - 镜头系统；
   - 开发预览和布局检查；
   - 向服务端发送玩家意图。

3. **数据包及可选资源包内容层**
   - 地图相关逻辑；
   - 任务；
   - 结构；
   - 奖励；
   - 游戏配置；
   - 页面和 HUD 数据；
   - 文本、动画、运镜及音效引用；
   - 通过受控接口响应模组事件。

### 4.2 权威边界

- 服务端模组是所有核心游戏状态的唯一权威来源；
- 客户端只显示服务端状态和提交操作意图，不能自行决定结果；
- 数据包不能直接修改模组的核心持久化状态；
- 不在记分板中复制一套独立生命周期或角色状态；
- 记分板、队伍和标签只作为兼容投影或只读查询出口；
- 所有高风险操作均由服务端重新验证权限、阶段、目标和确认令牌；
- 客户端显示为可点击，不代表服务端一定接受该操作。

### 4.3 范围控制

第一版不建设以下通用大系统：

- WebAdmin；
- 任意逻辑编辑器；
- 可执行任意客户端代码或脚本的 UI；
- 手机、图库等与本项目无关的系统；
- 拖拽式页面编辑器；
- 任意状态导入器。

需要的是足够支撑“全员逃走中”的可复用底座，而不是一个无限制的通用游戏引擎。

## 5. 游戏阶段与状态机

### 5.1 数据驱动阶段

模组只固定“没有有效游戏定义”“正常运行”“世界状态只读”等系统状态。具体游戏阶段由数据包用带命名空间的稳定 ID 注册，例如：

```text
pixel_tzz:setup
pixel_tzz:initializing
pixel_tzz:ready
```

数据包声明：

- 初始阶段；
- 阶段可见名称；
- 允许到达的相邻阶段；
- 进入和离开阶段的 `mcfunction` 回调；
- 各阶段可见的主持人和玩家面板操作。

第一里程碑持久化中的 `GamePhase` 枚举暂时作为旧存档兼容桥。它不再扩展，也不作为新游戏配置的定义来源；活动游戏和阶段真正接入时再进行一次显式、可恢复的存档 Schema 迁移。

### 5.2 状态机原则

- 阶段转换只能由服务端执行；
- 每个转换必须检查当前阶段、权限和前置条件；
- 重复请求不能造成重复转换；
- 过期界面发出的请求应被拒绝并刷新界面；
- 不依赖客户端动画结束来决定服务端阶段；
- 需要全体完成的阶段必须保留完成名单和未完成原因；
- 游戏结束条件暂不写死，由未来内容层通过安全事件请求触发。
- 所有人完成初始化或准备只会满足转换条件，不会自动转换阶段或开始游戏；
- 具体阶段定义缺失时保留原始阶段 ID，阻止不安全推进，不自动回退到默认阶段。

## 6. 主持人与管理控制

### 6.1 主持人

- 每个世界同时只有一名主持人；
- 主持人身份跨 `/reload` 持久保存；
- 世界无主持人时，任意 OP 可从图形化面板二次确认后原子认领；
- 不自动把服主、首个进入玩家或首个 OP 设置为主持人；
- 正常控制通过图形化面板完成，不要求主持人手敲命令；
- 主持人可以将权限转交给其他符合条件的玩家；
- 另一名 OP 可以在必要时接管主持人身份；
- 转交和接管均属于高风险操作，必须有明确确认与审计记录；
- 主持人默认不进入普通参与者初始化名单。
- 认领、转交或接管成功后，相关玩家的 ESC 入口与权限快照立即更新；成功者收到一次克制的 ActionBar 动画和音效反馈。

### 6.2 上下文控制台

主持人控制台不能是固定不变的按钮集合。打开时应根据当前阶段优先显示最可能需要的操作。

示例：

- `IDLE`：游戏配置、发起初始化；
- `INITIALIZING`：完成进度、未完成人员、猎人分配、锁定初始化；
- `INITIALIZATION_LOCKED`：检查角色、开放准备；
- `READY`：准备进度、未准备人员；
- `AWAITING_APPROVAL`：开局审批；
- `COUNTDOWN`：倒计时状态及取消；
- `RUNNING`：存活人数、捕获/复活状态、运行期控制；
- `ENDED`：结果与重置。

次要功能仍可进入，但首屏必须服务于当前阶段。

### 6.3 高风险操作二次确认

管理员按钮涉及高风险操作时必须二次确认。确认页不能只写“是否确认”，必须明确展示：

- 正在操作什么；
- 操作目标是谁或哪一轮游戏；
- 当前阶段；
- 将发生哪些状态变化；
- 哪些数据会保留；
- 哪些数据会清除或失效；
- 操作是否可撤销；
- 取消按钮。

适用操作至少包括：

- 发起强制初始化；
- 锁定初始化；
- 开放准备；
- 批准开局；
- 取消倒计时；
- 主持人转交或接管；
- 重置游戏；
- 恢复快照；
- 其他会改变多人状态的管理操作。

确认请求使用服务端签发的一次性、短时有效令牌。令牌绑定操作者、动作、目标和状态版本；重复使用或状态已经变化时必须拒绝。

### 6.4 数据包注册的上下文操作

数据包可以注册主持人或玩家面板操作，并声明：

- 分区、排序、按钮文本、说明、图标和语义色；
- 适用阶段；
- 控制显示与可用状态的数据包 predicate；
- 用户可读的禁用原因；
- 无目标、单选或多选目标模式；
- 按身份、队伍、生存状态、三类标签和流程完成状态筛选目标；
- 明确后果的二次确认；
- 发起流程、分配身份/队伍/生存状态、转换阶段或调用受检函数。

筛选器同一数组内使用 OR，不同非空数组之间使用 AND，空数组不增加限制。流程完成筛选按当前注册的“流程 ID + 版本”判断。

`enabled_when` 存在时必须提供 `disabled_reason`。没有 `enabled_when` 时仍可提供禁用原因，用于无合格目标、选择不足等框架内置禁用状态。

2A 只注册并校验这些操作，不在界面中显示或执行；后续执行器仍必须重新验证权限、阶段、目标、predicate、确认令牌和状态版本。

## 7. 加载、重载、重置与恢复

### 7.1 `/reload`

`/reload` 绝不能清除游戏数据。

执行 `/reload` 时：

- 重新解析数据包资源；
- 对候选资源进行完整校验；
- 只有全部成功才原子替换当前资源集；
- 资源有错误时继续使用上一份有效资源；
- 向主持人显示准确的资源路径和错误原因；
- 保留主持人、玩家初始化、角色、准备、存活和捕获状态；
- 如果正在倒计时，则继续使用启动时冻结的倒计时定义与状态，不用新 generation 替换，也不把 Reload 耗时计入倒计时；
- 已经开始的动画和运镜使用启动时快照，不因资源热重载中途变形；
- 游戏运行中新增的必填字段只对下一次显式重置后创建的运行生效，不能破坏当前实例。

### 7.2 数据包成功加载提示

数据包或当前游戏配置成功加载后，应播放精致但不过度打扰的加载提示：

- 使用 ActionBar；
- 字符逐个出现，形成打字效果；
- 颜色和节奏遵循统一视觉标准；
- 搭配同步、克制的 UI 音效；
- 加载失败时不播放成功动画，应显示诊断信息；
- 普通资源重载不能因此重置游戏状态。

具体文案、逐字速度、停留时间和音效资源在视觉原型阶段确定。

### 7.3 显式重置

游戏数据只能通过明确的重置操作清除：

- 使用主持人图形界面；
- 必须经过说明后果的二次确认；
- 提供“重置本局进程”：保留活动游戏和主持人，清除玩家初始化、身份、队伍、生存状态、准备、强制流程、阶段进度、任务、事件、回顾和独占预约，然后回到活动游戏初始阶段；
- 提供“清空 Pixel TZZ 全部数据”：连主持人、活动游戏和全部 Pixel TZZ 持久状态一起清除；
- 重置前创建一份最近恢复快照；
- 防止一次点击、过期页面或重复请求误触发；
- `/reload`、服务器重启和数据包更新都不能隐式触发任何一种重置。

### 7.4 持久化与恢复快照

- 数据按世界保存；
- 使用带版本号的持久化结构；
- 玩家记录以 UUID 为主键；
- 迁移或重置前保留一份最近恢复快照；
- 迁移失败不得覆盖原始数据；
- 主持人可通过详细二次确认恢复快照；
- 第一版提供只读诊断导出；
- 第一版不提供任意数据导入或通用存档编辑器。

## 8. 玩家初始化

### 8.1 启动方式

- 初始化不会因数据包加载或玩家进入自动开始；
- 只能由主持人在允许的阶段主动发起；
- 发起前显示详细二次确认；
- 发起时按流程受众规则锁定当时在线的实际参与者；
- 名单不会因普通上线或掉线自动改变分母；
- 后来上线者显示为“未纳入”，由主持人显式补充；
- 确定退出者可由主持人二次确认后从本次事件移除。

### 8.2 初始化入口

- 玩家不能自行选择猎人、逃走者或旁观者；
- 当前游戏默认身份是逃走者；
- 通用初始化当前只包含数据包注册的教程页面与最终确认；
- 暂不注册性别、称谓或其他尚无实际用途的剧情字段；
- 旁观者无需先完成初始化，由主持人面板直接设置；
- 队伍默认也只能由主持人设置，只有数据包明确注册“允许玩家自行选队”流程时才开放。

### 8.3 强制界面

- 初始化界面在需要玩家完成时不能通过 ESC、普通关闭按钮或重复打开其他菜单绕过；
- 玩家可以在初始化流程允许的页面间导航；
- 未通过服务端校验前不能伪造“已完成”；
- 客户端异常时必须有安全错误页、重试与重新同步能力，不能把玩家永久困在黑屏；
- 强制性来自服务端阶段与完成状态，客户端重连后仍会恢复正确页面。
- 每完成一页立即保存服务端进度；
- 玩家掉线、客户端重启或服务器重启后从上次未完成页面继续；
- `/reload` 不热替换正在运行的流程；当前实例继续使用发起时冻结的定义 generation。

### 8.4 身份初始化

- “通用初始化”和“身份初始化”是两个独立流程；
- 通用教程默认只面向数据包标记为参与者的身份；当前猎人偏后台，不参加通用流程；
- 主持人在通用初始化前即可多选玩家发起猎人初始化；
- 已是逃走者的玩家可转换为猎人，已有猎人也可重新初始化；
- 二次确认后只写入待转换状态，目标完成身份流程后才原子提交正式身份；
- 旁观者转换默认二次确认后立即生效，但数据包可以为它配置流程；
- 一个活动游戏同时最多存在一个未结束的强制流程实例；
- 当前实例结束或取消前，后发流程请求应明确拒绝，不建立玩家级或全局持久队列。

### 8.5 完成与人工调整

- 主持人能随时查看初始化完成进度；
- 主持人能查看未开始、进行中和离线的未完成玩家；
- 离线且未移除者仍在分母中；
- 主持人可显式补充或移除名单成员，所有操作记录操作者、目标和时间；
- 全部完成只标记初始化已完成，不自动进入准备；
- 主持人通过详细二次确认后进入准备阶段；
- 进入准备后仍允许调整身份或队伍，但被调整玩家的准备状态失效，必须完成对应流程后重新准备。
- 流程完成记录绑定流程 ID 与版本；数据包提高版本后，旧记录保留作历史，但玩家对当前版本重新视为未完成。

## 9. 数据驱动的自定义字段

### 9.1 固定字段与配置字段

模组核心固定管理：

- UUID；
- 最近使用的玩家名；
- 主持人身份；
- 当前活动游戏和阶段 ID；
- 身份、队伍和生存状态的命名空间 ID；
- 准备；
- 在线状态与时间信息。

地图或玩法特有字段由数据包中的版本化字段 Schema 定义，不写死在核心代码中。
流程选择先写入本次流程临时数据；只有字段显式声明为玩家持久字段时才跨流程、重启和 `/reload` 保留。

### 9.2 第一版字段类型

- 布尔值；
- 单选；
- 独占单选；
- 多选；
- 整数；
- 带范围限制的整数；
- 带长度限制的短文本；
- 资源标识符。

### 9.3 字段定义能力

字段定义至少可以描述：

- 稳定字段 ID；
- 显示名称和帮助文字；
- 类型；
- 默认值；
- 是否必填；
- 可见条件；
- 适用角色；
- 适用阶段；
- 玩家是否可编辑；
- 主持人是否可编辑；
- 数字范围或选项集合；
- 文本长度限制；
- 服务端验证规则；
- 修改后是否使准备失效；
- 数据版本及迁移策略。

表达式必须是受限、可验证的数据绑定或条件表达式，不允许执行任意 Java、命令或客户端脚本。
删除字段定义时保留已有原始值并标记为未解析，不自动清除或替换。

字段 `version` 必须为正整数。迁移策略默认 `preserve`；`reset_to_default` 必须同时提供满足当前类型和约束的显式默认值。2A 只注册并校验版本和策略，实际迁移在持久字段执行器接入后完成。

### 9.4 独占单选

`exclusive_choice` 用于多名玩家不能同时占用同一选项的持久选择。模组权威管理临时预约、改选和最终锁定，客户端或数据包不能通过普通字段写入制造重复占用。

- 选项、名称、说明、图标和预览页面由数据包注册；
- 同一游戏实例、字段和选项至多一个有效持有者；
- 选择时临时预约，流程最终完成后锁定；
- 改选必须原子释放旧临时值并占用新值；
- 掉线、重启和 `/reload` 不释放；
- 重新初始化期间保留旧锁定值，新流程成功后才原子交换；
- 角色不再适用该字段时可以按字段定义释放；
- 第一用途是猎人开局前选择唯一出生点，但核心不能写死猎人或出生点语义。

出生点只表示部署位置，不表示猎人是否已经释放。等待释放、已释放和释放批次继续由数据包注册的身份、队伍、生存状态、持久字段或标签组合表达，任务结果通过受控状态变更和回调执行；模组不理解猎人箱或释放条件。

## 10. 身份、队伍、状态与猎人指定

### 10.1 三个独立维度

- `role`：主要身份，例如数据包注册的逃走者、猎人、旁观者；
- `team`：身份内部的可选分队；
- `life_state`：存活、已捕获等独立状态。

主持人是世界级控制权限，不是主要身份。被捕玩家仍保留原身份和队伍，复活只恢复生存状态。

身份和队伍的可见名、说明、TAB 前缀、颜色、标签及允许关系由数据包注册；生存状态的可见名、说明和标签也由数据包注册。模组不识别“猎人”“存活”等显示文字，也不把具体身份或生存状态写入 Java 枚举。

### 10.2 猎人指定

- 当前默认身份由游戏定义注册为逃走者；
- 主持人在通用初始化前即可单选或多选玩家发起猎人初始化；
- 不需要等待其他玩家完成通用教程；
- 指定猎人、逃走者转猎人和猎人重新初始化均使用数据包注册的流程；
- 二次确认后仅建立待转换事务，玩家完成流程后才正式提交身份；
- 目标掉线时事务和流程进度保留，重连后继续；
- 已进入准备的玩家发生身份或队伍变化时，准备状态立即失效；
- 具体身份调整按钮、筛选条件、确认文案和流程绑定由数据包注册，服务端模组重新验证。

## 11. 准备与开局审批

### 11.1 开放准备

- 初始化锁定后，由主持人确认开放准备；
- 玩家准备页面属于强制流程，不能自行关闭；
- 玩家点击准备前应看到自己的已锁定信息和必要提示；
- 正常界面中一旦准备完成，玩家不能取消；
- 只有数据包受众规则选中的实际参与者进入准备分母；
- 当前配置下猎人、旁观者和主持人不阻塞准备；
- 主持人默认不能代替玩家准备；
- 框架可允许特殊数据包显式启用“主持人强制准备”，但当前配置不启用，且操作必须二次确认并审计。

### 11.2 掉线与准备

- 准备阶段参与者掉线会清除其已准备状态；
- 重连后恢复身份和初始化数据，但不会自动恢复准备；
- 掉线造成全员准备条件不再满足时，阶段应回到实际对应的等待状态；
- 观战者掉线不影响准备。

### 11.3 全员准备后

- 全员准备不会自动开局；
- 全员完成时进入数据包注册的“等待批准”阶段；
- 必须由主持人批准；
- 主持人批准开局属于高风险操作，必须经过详细二次确认；
- 确认页明确显示参与人数、猎人人数、逃走者人数、未满足的开局前要求，以及当前版本是否启用倒计时；
- 数据包可以注册身份所需的开局前持久字段，例如猎人独占出生点；
- 任一参与者未满足其开局前要求时，服务端必须阻止批准；
- 未配置 V3C 倒计时时，开局批准继续把冻结完整可达任务计划、固定本局参与者、进入起始阶段和启动首个环节作为一次原子事务完成；配置倒计时时，批准只原子冻结同一组内容并进入 `COUNTDOWN`，首个环节必须等倒计时完成后再原子启动。

### 11.4 V3C 正式开局倒计时

当前已完成的 2D 在主持人确认后立即原子批准；V3C 在 Game 显式引用倒计时定义时，把批准与
首个赛前环节之间扩展为服务端权威倒计时。未注册倒计时的旧数据包继续保持 2D 行为。

- 主持人批准时原子冻结参与者、可达任务计划、倒计时定义、回调集合和 LaunchPlan，然后进入 `COUNTDOWN`；
- 数据包声明倒计时引用为必需而对应资源无效时，批准必须失败，不能静默立即开局；
- 倒计时由服务端 Tick 和持久锚点推进，所有客户端动画只投影权威剩余时间；
- 倒计时固定显示在 ActionBar 基准线上方，不占用或清除原版/V3B ActionBar、Title 和 Subtitle；
- 时间最高显示到 `0.01s`，该小数只由客户端根据服务端锚点逐帧插值，不代表服务器超过 20 TPS；
- 变化数字可以逐位上下滚动，未变化位和分隔符保持稳定，低 FPS 时直接追到最新值；
- 冻结参与者永远属于显示受众，数据包和模组设置都不能隐藏；原版 F1 仍遵循原版 HUD 隐藏行为；
- 玩家可选择 full、simplified、static、高对比和独立倒计时音量，这些设置不改变权威时间；
- 倒计时不能由玩家或主持人跳过、快进，也不能以某个客户端动画播放完成作为开局依据；
- 主持人可以在阶段感知控制台中取消，但必须通过绑定倒计时实例 ID 与状态版本的二次确认；
- 取消后回到数据包注册的等待批准阶段，保留玩家准备和开局前字段，丢弃本次冻结候选；
- 参与者掉线策略由数据包在 `pause`、`cancel`、`continue` 中选择，默认暂停并等待同一玩家返回；
- 主持人掉线默认不影响倒计时，也可由数据包改为暂停或取消；
- `/reload` 保留正在运行的实例与冻结定义，新 generation 只影响下一次批准；
- 正常服务器关闭后恢复到专用等待状态，客户端尚未完成重连协调时绝不消耗剩余 Tick；
- 默认限制参与者移动、攻击、交互和物品操作并提供临时伤害免疫；镜头、聊天和 ESC 保持可用；
- 限制恢复不得改变游戏模式、写入永久效果或覆盖无关属性；
- 生命周期回调只在服务端执行，以实例、阶段、occurrence 和回调键记账，任何恢复路径都不得重复
  成功项；冷恢复的 `PENDING` 复用原 occurrence，`OUTCOME_UNKNOWN` 只能经明确提示重复副作用风险的
  独立高风险确认重试；
- 完成后的冻结 LaunchPlan 交接失败时必须保留可诊断实例，不得每 Tick 自动重复提交；主持人可以
  重试同一冻结候选，或高风险放弃并返回等待批准；
- 倒计时完成后才进入数据包注册的热身；热身结束后才启动全局游戏计时和第一个正式任务；
- 倒计时与热身均不计入全局游戏时长；热身可以拥有自己的独立计时；
- 取消、暂停、恢复、资源无效和人员缺失原因必须使用玩家可理解的文案投影。

## 12. 全体选择事件与主持人进度

任何需要一组玩家全部完成的事件都使用统一进度机制，包括但不限于：

- 玩家初始化；
- 玩家准备；
- 未来任务中的强制选择。

### 12.1 主持人进度条

当前主持人专属 BossBar 显示：

```text
<事件名称>: <完成数>/<总数>
```

要求：

- 事件名称、数字和状态使用统一且有语义的配色；
- 进度变化平滑；
- 正常、等待、即将完成、阻塞等状态可以有不同视觉反馈；
- 分母严格来自本流程锁定的实际参与者，不统计被受众规则排除的猎人、主持人或旁观者；
- 上下线不自动改变分母，离线且未移除者仍计入未完成；
- 名单增删后按主持人确认的结果更新；
- 玩家端不显示主持人专属管理信息。

流程可配置 BossBar 名称模板、原版颜色、原版分段样式、优先级和完成反馈；名称模板必须包含事件名、完成数和总数占位符，完成反馈可以配置文本、颜色、停留 Tick 与声音 ID。多个受跟踪流程可同时显示。未来自定义 HUD 可以增强节目效果，但不能取消这里已经确认的主持人 BossBar。

### 12.2 未完成人员

主持人控制台提供：

```text
查看未完成人员（n）
```

进入后显示：

- 玩家头像与名称；
- 在线/离线；
- 当前完成状态；
- 未开始、进行中或离线分类；
- 缺少的具体字段、节点或步骤；
- 最后状态时间；
- 当前是否阻塞全体进度。

离线玩家的信息来自持久化记录，不依赖其当前在线。

## 13. 上下线与玩家记录

### 13.1 UUID 玩家记录

每名相关玩家持久化保存：

- UUID；
- 最近使用的玩家名；
- 参与或观战选择；
- 角色；
- 初始化字段；
- 准备状态；
- 存活、捕获和复活状态；
- 在线/离线状态；
- 相关状态更新时间；
- 当前轮次标识。

### 13.2 掉线提醒规则

| 玩家状态 | 掉线处理 |
|---|---|
| 尚未初始化 | 不提醒 |
| 观战者 | 不提醒 |
| 已初始化参与者 | 提醒主持人 |
| 已准备参与者 | 提醒主持人并清除准备 |
| 倒计时中的参与者 | 按冻结定义执行 `pause`、`cancel` 或 `continue`；默认暂停等待 |
| 游戏中存活逃走者 | 记录并提醒，不自动判定被捕 |
| 主持人 | 倒计时默认继续；配置为暂停或取消时按冻结策略处理，其他阶段保留游戏数据 |

重新连接时恢复其身份、初始化字段、角色和运行状态。被掉线规则明确清除的准备状态不恢复；
进入 `COUNTDOWN` 后使用冻结参与者与准备结果，不再套用批准前“掉线清除准备”的规则，而是
执行 Countdown 冻结的 `pause`、`cancel` 或 `continue` 策略。

## 14. 捕获、死亡旁观与复活

### 14.1 捕获判定

- 正在游戏中的存活逃走者遭遇任何致死结果，都算被捕；
- 不区分猎人攻击、环境伤害、指令伤害或其他死亡原因；
- 猎人或观战者的死亡不套用“逃走者被捕”语义；
- 对同一名玩家的重复致死事件只能成功处理一次；
- 捕获状态流转为：

```text
ALIVE → CAPTURING → CAPTURED
```

### 14.2 不进行原版真实死亡

致死结果由模组在安全时机拦截：

- 不进入原版死亡界面；
- 不掉落物品；
- 不丢失经验；
- 不执行原版重生传送；
- 屏蔽对应的原版死亡提示；
- 捕获动画期间暂时冻结并保护玩家；
- 动画结束后进入被捕后的旁观状态；
- 不依赖死亡后再把玩家传回原位置。

服务端必须防止其他模组、重复伤害或网络重试造成重复捕获和重复广播。

### 14.3 捕获消息

正常聊天历史中依次记录：

```text
<玩家名> 被猎人捉捕！
还有 <数量> 名逃走者仍在逃亡。
```

要求：

- 第一行使用深红色；
- 第二行突出剩余数量；
- 剩余数量只统计当前存活逃走者；
- 已捕逃走者仍属于逃走者角色，但不计入存活数量；
- 消息可以使用动态聊天动画，但最终内容必须留在普通聊天历史中。

### 14.4 捕获镜头

默认捕获镜头约 2.5 秒：

1. 保留玩家身体在捕获点；
2. 受害者视角平滑切换为第三人称；
3. 镜头看向自身捕获位置；
4. 镜头向后、向上缓慢拉远；
5. 结束时平滑交接到被捕后的旁观视角。

碰撞与异常空间处理：

- 使用多射线或连续碰撞检测避免镜头穿墙；
- 后方受阻时尝试替代角度；
- 空间狭窄时缩短距离；
- 接近虚空或找不到安全机位时使用短拉远、FOV 变化或淡出；
- 不能把镜头卡进方块；
- 断线、重载或动画取消时恢复正常相机状态；
- 开启“减少动态效果”时使用约 0.5 秒的简化过渡。

### 14.5 复活

- 未来任务可以请求复活已捕逃走者；
- 复活将 `CAPTURED` 恢复为 `ALIVE`；
- 玩家角色始终保持逃走者；
- 恢复可游玩状态、TAB 状态及存活人数；
- 对已经存活的玩家重复复活不得产生副作用；
- 复活细节通过受控模组接口完成，数据包不能直接篡改核心状态。

### 14.6 零存活者

存活逃走者变为 0 时，模组发出标准事件钩子。第一版核心不直接写死游戏结束，因为最终结束规则仍取决于未来主线和任务设计。

## 15. TAB 玩家列表

TAB 样式必须来自数据包定义，不根据“猎人”“逃走者”、固定标签或 Java 枚举推断。身份、队伍和生存状态可以分别注册前缀、名称颜色、排序优先级及覆盖方式，按下列顺序合成：

```text
role → team → life_state → host system override
```

要求：

- 前缀显示在玩家名称前；
- 主持人是系统权限，始终以金色 `[主持人]` 最高优先级显示；
- 身份可以绑定初始化流程，只有本次身份提交带有匹配流程 ID、版本和成功实例凭据后才公开身份前缀、颜色和身份排序；更早的历史完成不能绕过本次重新初始化；
- 没有初始化流程的身份可以立即公开；
- 未公开身份不添加前缀、不修改颜色，也不打乱玩家的初始自然顺序；
- 队伍和生存状态可以补充或覆盖身份样式；
- 角色和存活状态变化后及时同步；
- 复活后按保留的身份、队伍和新的生存状态重新合成样式；
- 不能只靠颜色传达信息，前缀文本必须保留；
- 不修改玩家 UUID 或真实名称；
- 与其他模组的 TAB 扩展发生冲突时应提供诊断和可配置降级方式。

第一套正式数据包推荐呈现主持人、猎人、逃走者、旁观者从上到下排序，猎人红色、逃走者绿色、旁观者灰色；这是内容配置，不是核心写死规则。

## 16. UI 视觉与交互标准

### 16.1 风格

总体风格为克制、清晰的“电视节目控制台”：

- 有节目感；
- 信息层级明确；
- 颜色和谐；
- 不使用无意义的彩虹色堆叠；
- 动画精致但不拖慢操作；
- 玩家端更沉浸，主持人端更强调状态和风险。

2B～2D 主持人管理侧现有完成度是 V3 玩家侧的最低质量基线。玩家侧虽然通常不涉及全局配置、权限裁决和复杂名单，但不能因此使用简陋控件、占位排版或缺少状态反馈；其长期暴露在整局游戏中，应在视觉、动画、声音、连贯性和异常恢复上达到相同或更高水准。

V3 统一质量基线只确认一次，后续所有玩家页面、HUD、动态文本和演出自动继承，不要求用户在每个页面重复强调。详细要求见 `docs/MILESTONE-3-PLAN.md`。

### 16.2 核心色板

| 语义 | 颜色 |
|---|---|
| 品牌金 | `#F4C95D` |
| 信息青 | `#64D8E8` |

颜色必须按语义使用，同一状态在 GUI、HUD、Title、聊天和提示音中保持一致。

### 16.3 动画标准

适合覆写的区域应提供比原版更细致的动画：

- 字符逐个出现；
- 白色向红色等逐字或逐区域颜色填充；
- 连续渐变；
- 淡入淡出；
- 平滑尺寸和位置变化；
- 进度条平滑过渡；
- Title 与 HUD 的同步节奏；
- 动画关键点配合声音。

动画速度应连续、可调整，不使用生硬的少数速度档位。任何动画都不能延迟服务端真实状态或阻碍紧急操作。

### 16.4 ESC 入口

- 自定义系统在 ESC 中注册稳定入口；
- 主持人打开上下文相关的控制台；
- 所有非主持人玩家打开数据包注册的上下文玩家终端；
- 非主持人 OP 仍使用玩家终端，只额外获得一个低优先级、不可被数据包伪造或隐藏的主持人接管按钮；
- 被强制进行初始化或准备时，ESC 应回到当前强制页面，而不是允许退出流程；
- 游戏结束后可以按服务端上下文进入赛后回顾；
- 入口名称、权限和目标页面必须随服务端状态实时更新，不要求关闭并重新打开 ESC；
- 原版必要按钮仍应可用，不能破坏正常退出游戏、辅助功能和错误恢复。

### 16.5 动态页面

页面必须支持：

- 服务端状态实时更新；
- 动态文字；
- 动态按钮标签；
- 按状态显示或隐藏；
- 不可用状态及明确原因；
- 玩家头像、图标和状态；
- 可滚动玩家列表；
- 键盘导航；
- 不同 GUI 缩放和窗口尺寸；
- 加载、空状态、错误和重连状态；
- 主持人/玩家/观战者不同上下文。

### 16.6 V3 玩家终端

- 玩家终端不是缩小版主持人控制台，不显示全局配置、完整玩家名单、未来任务、隐藏分支、回调审计和内部 ID；
- 强制流程期间玩家已经锁定在强制页，不进入玩家终端，也不在终端重复显示强制流程；
- 普通玩家终端不因任务、事件或身份变化自动弹出，并可随时关闭；
- 玩家终端打开哪一页、页面内部按钮打开哪一页，均由数据包通过受检路由注册；
- 当前任务、个人数据、历史事件、详情、帮助和任务操作都是独立配置项，不存在模组写死的标准任务卡或个人资料卡；
- 当前页面失效时根据最新服务端路由平滑切换；普通状态更新尽量原地完成，不重建整页；
- 捕获或紧急运镜可以安全关闭普通终端取得画面控制权，但不能随意中止服务端强制流程；
- 玩家按钮可以请求执行数据包注册函数；服务端必须重验页面、玩家、阶段、任务、受众、条件、次数、冷却和防重放；
- 注册函数可以修改 Minecraft 世界，但不能直接改写模组权威状态。

当前任务玩家视图、历史事件、个人数据、路由和注册函数的完整已确认要求见 `docs/MILESTONE-3-PLAN.md`。

## 17. 数据驱动布局系统

### 17.1 目标

自定义 GUI 不只用于开局面板，还要能复用于后续任务、游戏配置和新版本创意。因此页面不能全部写死在 Java 中。

### 17.2 职责分工

Java 提供安全组件、布局引擎、数据绑定、事件请求和渲染能力；页面通过数据资源描述：

- 布局；
- 样式；
- 文字；
- 动画；
- 数据绑定；
- 可见条件；
- 按钮动作 ID；
- 响应式规则。

数据资源不能包含任意脚本或任意 Java 调用。

### 17.3 布局能力

第一版布局系统目标支持：

- Row；
- Column；
- Grid；
- Flow；
- Scroll；
- Card；
- Overlay；
- 最小/最大尺寸；
- 固定、内容、自适应和比例尺寸；
- 边距、间距、对齐；
- 锚点；
- 响应式断点或约束；
- 长列表虚拟化。

Split 由 Row/Column 加权重表达，垂直堆叠使用 Column，层叠使用 Overlay。第一版不建设含义重叠的 Split 或 Stack 运行时；未来确需简写时只能在编译阶段降低为上述核心布局。

### 17.4 页面扩展

- 核心页面和任务页面使用同一文档格式；
- 数据包可以添加或覆盖被允许的页面资源；
- 所有页面在启用前必须通过 Schema、资源引用和复杂度校验；
- 服务端只接受注册过且在当前状态允许的动作 ID；
- 数据包页面不能绕过服务端权限；
- 第一版提供预览器和布局检查器；
- 第一版不提供拖拽式页面编辑器。

## 18. 动态文字演出

### 18.1 核心行为

V3B 采用“先注册、后调用”。一个稳定演出 ID 可以打包多个 Chat、Title、Subtitle、
ActionBar、声音和服务端回调，并让各内容同时或按时间线播放。

动态 Chat 必须是真正进入原版聊天历史的可更新系统消息，不是盖在聊天框上方的独立假聊天层：

1. 服务端验证演出 ID、受众、参数、条件和上下文；
2. 服务端只向每名玩家发送其获准看到的专属演出包；
3. 客户端在聊天历史中插入一个逻辑条目；
4. 动画帧持续原地更新这个条目；
5. 动画结束后最终文本保留在历史中。

普通玩家聊天可以把活动动态条目向上顶，条目滚出可见区域后仍有界完成。普通 `tellraw`、普通
系统消息和签名玩家聊天保持原行为，不会自动获得动画。V3B 遵守原版聊天可见性、布局、容量
和隐私设置，不建立第二套永久聊天历史。

Title、Subtitle 和 ActionBar 可以使用原版安全位置、受控偏移、宽度和多行间距，但不能借
V3B 注册任意常驻 HUD。常驻 HUD 已延期为未来独立目标，不属于当前纯倒计时 V3C。

### 18.2 资源、文本与动态数据

V3B 新增独立的动画预设和演出资源。每个资源一项一文件，遵循数据包优先级，高优先级同 ID
文件完整覆盖低优先级文件，不进行隐式深度合并。

文本建立在原版文本组件上，支持适用的：

- 普通文本、翻译和参数；
- Score；
- Selector；
- NBT/Data，以及 Storage、实体和方块来源；
- Keybind；
- 子组件、字体、样式；
- Hover、Click 和 Insertion 事件。

动画期间只有已显示字符具有交互。动态参数必须具名、带类型、来源和回退；可以读取调用参数、
执行上下文、Scoreboard、Storage、任务、统计、事件和 V3A 已授权个人字段。客户端不能提交
任意动态文本、任意目标或函数名。

### 18.3 动态字段取值

每个内容块可以选择：

- 内容开始时一次性锁定全部动态字段；
- 第一个动态字段播放前 1 Tick 锁定全部字段；
- 每个动态字段在自己播放前 1 Tick 获取最新值并分别锁定。

字段一旦开始显示便不再变化。相同字段 ID 默认共享锁定值；需要后续重新取值时必须使用局部
字段或不同字段实例。取值到显示之间不能出现旧值闪烁、空占位或额外停顿。

内容可以使用服务端条件和有序变体选择文案。客户端只收到命中分支。不同客户端语言可以显示
不同译文，但服务端回调不依赖客户端报告的文本长度。

### 18.4 动画、排版与声音

首版提供：

- 多行打字机；
- 可配置光标块、颜色、闪烁和速度；
- 新字临时颜色、保持字符距离，以及瞬切或渐变恢复最终颜色；
- 透明度、颜色填充、颜色渐变；
- 原版乱码逐字解码；
- 分段延迟、重点停顿；
- 轻微滑入、缩放和单次脉冲；
- 开始音、关键帧音、结束音、字符音和独立声音节点。

光标块和新字颜色是独立配置。最终文字必须恢复原组件逐段样式。声音轨明确指定主字符音来源，
不能因为多个通道并行而自动重复声音。

动态内容使用预排版避免打字时反复挤动已显示行。未取值字段可以声明预计宽度或最大长度，超出
时按配置换行、缩小、省略或静态降级。字符计数使用可见字素，不拆坏中文、Emoji 和组合字符。

所有时间必须有 Tick、秒或毫秒单位。视觉动画允许小于 1 Tick 的平滑间隔，服务端回调只能在
到期后的完整 Tick 执行。

### 18.5 时间线、并发与控制

演出可以立即、多人同步或按玩家屏幕条件开始；迟到客户端跳到标准时间线当前帧。演出可以使用
游戏时间或单调表现时间。带权威流程回调的演出默认使用游戏时间，纯提示默认使用表现时间。

每个内容注册优先级和以下冲突策略：

- 并行；
- 排队；
- 替换；
- 丢弃。

Chat 默认并行，Title、Subtitle、ActionBar 默认排队。同 ID 重复调用可以允许、忽略活动中
重复、重播、排队或刷新，并可注册冷却和去重键。默认忽略同目标、同关键参数的活动中重复调用。

数据包可以按实例、ID、分组或目标暂停、继续、补全和取消。Chat 被中断时默认补全最终文本，
也可完整移除尚未完成条目；不能永久留下半句话。V3B 只允许有限重复，无限常驻内容属于 HUD。

### 18.6 服务端回调与联动

演出可以注册开始、关键帧、每名玩家完成、全部目标完成和中断回调。回调只运行数据包注册函数，
并以服务端标准时间线执行，不等待客户端确认。回调执行上下文、调用原点、目标、参数、状态和
中断原因必须明确；失败默认不重试。

动态演出可以可选写入玩家历史或赛后回顾，也可以由任务、阶段、强制流程、初始化、暂停和结束
等已有权威事件直接引用。缺少注册时，模组不能自动生成正式文案。

### 18.7 受众、上下文与安全

演出和每个内容块分别配置受众。受众可以固定、只增加或严格实时重新验证。身份秘密强制最小
权限投影，其他身份文本、未命中分支、隐藏参数和回调函数名不能下发客户端。

游戏阶段限制默认关闭；只有数据包注册允许上下文时才验证。排队内容在实际开始前重新检查已
声明限制。普通玩家和客户端不能绕过，受信任函数、服务端控制台和主持人预览可以显式绕过。

空受众、离线目标、无效参数和缺失资源必须有明确失败或降级策略。默认空受众调用失败、离线
目标跳过。非主持人 OP 仍只有普通玩家权限，必须先正式接管主持人才能使用 V3B 管理工具。

### 18.8 生命周期、辅助功能与兼容

每个内容可在播放前等待游戏画面、关闭普通模组页面或静态降级；强制流程不能被普通文字擅自
关闭。播放中被界面遮挡时，Chat 默认继续，其他通道默认暂停。

重连、晚加入、Reload、服务器重启、维度切换、传送和重生分别具有继续、重播、补全、取消或
丢弃策略。活动调用固定编译快照；持久化实例必须保存字段值、进度和已执行回调，避免重复推进。

玩家可以调节速度、减少动态、关闭字符音和光标闪烁、提高对比度，并对获准消息执行“立即补全”。
最终内容不能被隐藏。补全按键默认不绑定，数据包不能强占玩家键位。讲述人只朗读最终文本一次。

V3B 不拦截或清除其他模组与原版的 Title、Subtitle、ActionBar。动态 Chat 无法与某个聊天
模组安全原位更新时，直接显示一次最终静态文本，不逐帧刷屏。Chat Heads 等装饰条目元数据的
模组应保持兼容并进入实机矩阵。

主持人拥有默认无副作用的预览器与诊断命令。普通无效资源只隔离该 ID；数据包可以把关键演出
标记为必需。普通玩家不显示红色错误窗口。

### 18.9 容量与实施文档

模组设置不可突破的字符、行、内容块、时长、并发、队列、声音、回调、条件和持久化硬上限；
数据包可以设置更低软上限。超限优先显示最终文本。具体数值通过压力测试确定，不提前拍脑袋
固定。动画不能每 Tick 扫描完整聊天历史。

完整 V3B 默认值、实施分段、预览器、兼容矩阵、验证计划和完成定义见
[`MILESTONE-3B-PLAN.md`](MILESTONE-3B-PLAN.md)。正式 JSON Schema、命令拼写、协议、状态
迁移和示例已经写入 [`DATA-PACK-MESSAGE-API-3B.md`](DATA-PACK-MESSAGE-API-3B.md)。

## 19. 倒计时系统与专用显示层

V3C 不建设常驻 HUD。原“右下角信息坞、HUD 组件、路由和布局编辑”原型只保存在
`codex/milestone-3c` 分支的 `e66b92d`，不属于当前主线 API。当前任务、个人资料和过去事件
继续由 V3A 玩家终端承担，普通临时文字继续由 V3B 承担。

### 19.1 通用核心与唯一公开特化

- 核心处理 instance、purpose、权威时间、受众、限制、Checkpoint、回调和恢复；
- 当前唯一公开 purpose 是 `opening`，由 Game 的 `opening_countdown` 接入；
- 数据包不能任意创建实例、填写 purpose 或调用内部完成处理器；
- 全局同一时刻最多一个非终态倒计时；
- 第二个启动请求明确失败，不覆盖、不合并、不排队；
- 玩家和主持人均不能跳过、快进、立即完成或修改剩余时间；
- 主持人只可通过绑定实例和状态版本的高风险二次确认取消。

### 19.2 固定 ActionBar 上方显示

- 模组使用独立 Overlay，固定在原版 ActionBar 基准线上方；
- 不向 ActionBar、Title 或 Subtitle 写入内容，也不拦截、清除或延长其他模组的内容；
- ActionBar 有无文字都不改变倒计时基线；
- 普通文字大小参考 ActionBar，数字只能有限突出；
- 默认只占一条主行和一条可选细进度线；
- 不提供任意坐标、组件树、输入、点击、滚动正文或大面积中央面板；
- 2K 保持基准比例，小窗等比缩小，大屏有最大尺寸；
- F1 按原版隐藏整个 HUD，再打开时直接恢复当前值，不重播旧动画。

### 19.3 时间和逐位动画

- 服务端始终以 20 TPS 推进权威 remaining；
- 数据包可选择整数、十分位或百分位，最高 `0.01s`；
- 小数由客户端根据服务端 Tick 锚点和单调时钟逐帧插值，不代表服务器达到 100 TPS；
- 数字使用固定宽度，每个变化位拥有独立裁切窗口；
- 默认新数字从上方进入、旧数字向下退出；
- 未变化位、冒号和小数点不动；
- 借位、暂停、低 FPS、重连和网络校正不积压过期动画；
- 客户端动画不能推动完成或开局。

### 19.4 数据包表现能力

数据包可以独立配置标题、前缀、后缀、等待/暂停/完成文案、总时长、格式、精度、补零、颜色、
背景、描边、安全间距、内边距、最大宽度、数字比例、逐位动画、细进度线、进入/退出/完成表现、
Checkpoint 声音和生命周期回调。

所有尺寸、Alpha、位移、闪烁、动画时长、音量、文本、Checkpoint 和 Callback 都有模组硬上限。
数据包不能改变固定显示区域、隐藏冻结参与者、突破高对比/静态降级或把透明度降到不可读。

### 19.5 玩家设置与辅助功能

设置层级固定为 `选项 → 全员逃走中设置 → 开局倒计时`，提供：

- full、simplified、static 三档动态强度；
- 高对比；
- 独立倒计时音量；
- 无副作用实时预览；
- 重置和诊断。

模组设置不提供完全隐藏、位置拖动、透明度 0、修改时间、改变受众、跳过或快进。Static 只删除
动画，不删除正文和剩余时间。冻结参与者永远属于显示受众；数据包也不能关闭该下限。原版 F1
继续遵循原版 HUD 隐藏行为。

### 19.6 权威开局顺序

- 主持人批准时原子冻结参与者、倒计时定义、限制、回调、任务 DAG 和 LaunchPlan；
- required 定义无效时阻止批准，optional 降级必须明确审阅；
- 倒计时完成并结清 required callbacks 后才提交冻结 LaunchPlan；
- 有 warmup 时先进入 warmup，无 warmup 时直接启动 first main；
- 倒计时和 warmup 都不计入全局游戏时长；
- warmup 结束后，game clock 与第一个计时 main task 原子启动；
- `/reload` 使用冻结 generation；正常重启先进入 recovery wait；离线时间不计入 remaining；
- 限制、回调和恢复都必须幂等，不能重复开局。

完整产品边界、数据包契约和测试见：

- [`MILESTONE-3C-PLAN.md`](MILESTONE-3C-PLAN.md)

## 21. 音效与资源资产

### 21.1 音效原则

- 音效与视觉状态使用统一语义；
- 打字音不能对每个字符都制造刺耳噪声，应支持节流或按节奏采样；
- 关键确认、警告、危险、成功和倒计时使用不同声音语言；
- 客户端动画音效与动画时间轴同步；
- 服务端关键事件仍有稳定时间基准；
- 音效缺失不能阻断功能。

### 21.2 资产策略

原型阶段：

- 优先使用合适的原版声音；
- 用资源 ID 引用，不把文件路径写死在代码中。

正式阶段：

- 优先制作原创合成 UI 音效包；
- 如果必须使用外部素材，逐项记录来源、作者、许可证、是否可修改和是否要求署名；
- 项目保留许可证清单和 notices；
- 未确认授权的素材不得进入仓库和发布包。

最终音效来源以后单独研究，目前不提前锁定。

## 22. 游戏配置（Game Profile）

同一个核心模组支持可替换游戏配置。每个配置可以定义：

- 稳定 ID；
- 显示名称；
- 配置版本；
- 所需模组 API 版本；
- 主题；
- 初始化字段；
- 角色要求；
- 倒计时及规则参数；
- 页面；
- 未来独立目标重新注册的常驻 HUD（不属于当前 V3C）；
- 动态消息；
- 运镜；
- 音效；
- 单任务时间线入口、有限任务 DAG 与双 Tick 计时规则；
- 任务、结果、间隔、事件、统计与赛后回顾；
- 开局前必填字段要求；
- 数据包事件钩子；
- 资源依赖。

规则：

- 一套实际运行的正式数据包资源集合只注册一个 Game Profile；
- 没有游戏定义时显示明确诊断；
- 同时出现多个游戏定义时视为内容配置冲突，不能让客户端选择或静默猜测；
- V3 不提供首次配置选择页，也不提供 `IDLE` 阶段的配置切换页；
- 配置不兼容或校验失败时保留当前有效配置；
- 未来“全员逃走中 2.0”通过更换数据包、资源包或世界内容实现，仍复用核心模组。

### 22.1 单任务时间线

- 一个活动游戏同时只有一个任务或赛前环节；
- 任务路线必须是有限有向无环图，不允许循环或跳过；
- 赛前环节与主任务使用同一框架，但可以不计正式游戏时间；
- 当前环节时间与正式游戏时间均使用有效服务器 Tick；
- 服务器停机和主持人主动暂停期间不流逝，`/reload` 不暂停；
- 每个任务最终只冻结一个全局结果，由数据包通过受控接口提交；
- 结果原子决定下一任务、间隔和阶段转换；
- 到时后数据包没有提交结果时停留在结算异常，模组不能猜测结果；
- 间隔结束后默认自动进入下一任务，主持人可二次确认延长或提前结束；
- 最终任务经过可配置最终间隔后进入数据包注册的结束阶段；
- 主持人可查看完整时间线，普通玩家默认不可查看实时时间线；
- 赛后回顾只显示本局实际发生的任务、事件和统计，并保留到显式重置；
- 已完成游戏存在时不能自动覆盖或直接开始第二局。

## 23. 数据包桥接

### 23.1 模组向数据包提供

- 版本化事件回调或函数钩子；
- 安全命令或等价动作接口；
- 当前阶段和只读状态查询；
- 角色、参与、在线、存活、捕获状态的标签/队伍/记分板投影；
- 打开注册页面；
- 播放注册动态消息；
- 播放注册运镜；
- 请求复活；
- 请求结束游戏；
- 任务结果提交；
- 任务事件与统计写入；
- 当前任务、双 Tick、结果、间隔和回顾的只读查询；
- 任务全局回调和受检逐玩家字段回调；
- 独占选择预约状态；
- 任务动作回调。

### 23.2 数据包限制

- 不能直接编辑核心持久化文件；
- 不能绕过服务端状态机；
- 不能直接宣称玩家准备、存活或复活成功；
- 不能直接改写权威任务 Tick、冻结结果、路由、回顾或独占预约；
- 不能执行未注册的 UI 客户端动作；
- 所有资源 ID、参数、目标玩家和调用阶段必须校验；
- API 发生不兼容变化时必须升级主版本并提供清楚诊断。

### 23.3 投影原则

兼容标签、队伍和记分板由模组生成，外部修改不会反向成为核心事实。发生偏差时模组应在下一次相关状态变化时纠正，并可在开发诊断中报告。

## 24. 网络、安全与审计

### 24.1 网络

- 使用明确版本的客户端/服务端协议；
- 登录或进入世界时完成能力握手；
- 客户端缺失、版本不匹配或资源能力不足时给出明确错误；
- 同步采用状态快照加增量更新；
- 不每 Tick 广播完整玩家列表；
- 页面打开后订阅其需要的数据，关闭后释放；
- 动画和运镜尽量在客户端执行，服务端只同步开始时间和权威事件。

### 24.2 信任边界

- 网络请求使用有类型的动作；
- 校验操作者、权限、阶段、目标、参数和资源 ID；
- 高风险动作使用一次性确认令牌；
- 拒绝过期、重放和状态版本不匹配的请求；
- 限制单包大小、字符串长度、列表长度和调用频率；
- 限制 UI 文档节点数、嵌套深度和表达式复杂度；
- 不接受客户端提交的“我是猎人”“我已准备”等最终状态。

### 24.3 审计

至少记录：

- 时间；
- 操作者 UUID 和名称；
- 操作类型；
- 目标；
- 操作前后阶段；
- 成功或拒绝；
- 拒绝原因；
- 相关轮次 ID。

普通字符动画帧、HUD 插值等纯客户端行为不进入服务端审计。

### 25.1 人数目标

- 缓存需要有清晰失效条件；

11. 页面按钮只提交 Local、Flow 或 Registered 三类有类型意图，2B 不执行真实操作；

16. 2B 不执行初始化、准备、猎人指定、面板操作或 BossBar，不修改任何权威游戏状态；
17. 页面下发、预览目录和资源报告使用网络协议 v5；

20. `clip_progress` 当前固定从左向右揭示，`scale` 只进行围绕节点的几何缩放，不触发布局重排或字号重新测量；

23. 当前基础示例包含 `31` 个文件和 `23` 项 Pixel TZZ 定义。

## 29. 验收总原则

每项功能同时满足以下条件才算完成：

1. **行为正确**：服务端状态符合本文档；
2. **异常安全**：掉线、重载、重复请求和资源错误不会破坏数据；
3. **界面一致**：颜色、文字、动画和声音遵循统一标准；
4. **权限可靠**：客户端或数据包不能绕过服务端；
5. **性能有界**：人数、节点、消息和动画量均有明确上限；
6. **可扩展但不过度设计**：地图和任务可通过内容层扩展，核心不建设无关通用系统；
7. **可验证**：自动检查与实际进世界测试均有记录；
8. **不擅自定案**：地图、任务、主线和未确定资产继续保持可替换。
