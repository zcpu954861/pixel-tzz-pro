# 全员逃走中-扩展：模组与数据包需求规格

> 文档状态：持续维护的需求基线（第一里程碑与第二里程碑 2A、2B、2C 已通过用户实机验收；2D 框架与自动检查已完成，待用户实机验收）
> 项目版本：`0.1.0`
> 目标 Minecraft 版本：`26.2`
> 最后整理：2026-07-28

## 1. 文档目的

本文档记录“全员逃走中-扩展”模组及其配套数据包目前已经对齐的完整要求，作为后续设计、开发、验收和扩展时的统一依据。

文档中的要求分为三类：

- **已确认**：后续实现必须遵守，修改时需要重新确认。
- **实现约束**：不限定具体代码写法，但最终行为必须满足。
- **待确定**：当前没有定案，不得在实现时擅自写死。

第一里程碑与第二里程碑 2A、2B、2C 已经完成并通过用户实机验收；2D 框架代码与自动检查已完成，仍待用户逐项 Minecraft 实机验收。

## 2. 项目定位

### 2.1 核心目标

本项目用于制作 Minecraft 版“全员逃走中”的通用运行底座，重点提升：

- 开局前流程的完整性和可控性；
- 玩家与主持人的界面体验；
- 动画、文字、声音、镜头等节目化表现；
- 状态持久化、异常恢复和多人环境可靠性；
- 后续地图、任务和新玩法的复用能力；
- 相比纯数据包更自由、更连贯的客户端表现。

项目不是只服务于当前一张地图。未来“全员逃走中 2.0”或其他变体应尽量通过新游戏配置、数据包及资源包实现，而不是复制并分叉整个模组。

### 2.2 旧项目的使用边界

旧仓库：

- <https://github.com/zcpu954861/1.21.11-tzz_game_datapack>

旧项目只用于帮助理解已有经验、玩法语境和曾经遇到的问题，不复用：

- 旧地图；
- 旧任务；
- 坐标与结构；
- 旧流程；
- 旧代码；
- 为旧项目写死的架构。

本项目是一次独立、从零设计的新实现。

### 2.3 已知但尚未确定的内容

以下内容尚未定案：

- 正式游玩的主线；
- 地图；
- 具体任务；
- 复活任务的规则与内容；
- 最终音效资产；
- 具体游戏结束条件；
- 各游戏配置中的自定义字段；
- 远距离运镜所需区块加载方案的最终选择。

这些内容不得提前写死到模组核心。

## 4. 总体架构

### 4.1 组成

项目采用三层结构：

1. **服务端模组核心**
   - 游戏阶段；
   - 主持人；
   - 玩家身份与自定义数据；
   - 准备状态；
   - 角色；
   - 存活、捕获、复活状态；
   - 权限校验；
   - 持久化；
   - 数据包桥接；
   - 网络请求的最终裁决。

2. **客户端模组表现层**
   - 自定义 GUI；
   - HUD；
   - 动态聊天文本；
   - 动画与音效；
   - 镜头系统；
   - 开发预览和布局检查；
   - 向服务端发送玩家意图。

3. **数据包及可选资源包内容层**
   - 地图相关逻辑；
   - 任务；
   - 结构；
   - 奖励；
   - 游戏配置；
   - 页面和 HUD 数据；
   - 文本、动画、运镜及音效引用；
   - 通过受控接口响应模组事件。

### 4.2 权威边界

- 服务端模组是所有核心游戏状态的唯一权威来源；
- 客户端只显示服务端状态和提交操作意图，不能自行决定结果；
- 数据包不能直接修改模组的核心持久化状态；
- 不在记分板中复制一套独立生命周期或角色状态；
- 记分板、队伍和标签只作为兼容投影或只读查询出口；
- 所有高风险操作均由服务端重新验证权限、阶段、目标和确认令牌；
- 客户端显示为可点击，不代表服务端一定接受该操作。

### 4.3 范围控制

第一版不建设以下通用大系统：

- WebAdmin；
- 任意逻辑编辑器；
- 可执行任意客户端代码或脚本的 UI；
- 手机、图库等与本项目无关的系统；
- 拖拽式页面编辑器；
- 任意状态导入器。

需要的是足够支撑“全员逃走中”的可复用底座，而不是一个无限制的通用游戏引擎。

## 5. 游戏阶段与状态机

### 5.1 数据驱动阶段

模组只固定“没有有效游戏定义”“正常运行”“世界状态只读”等系统状态。具体游戏阶段由数据包用带命名空间的稳定 ID 注册，例如：

```text
pixel_tzz:setup
pixel_tzz:initializing
pixel_tzz:ready
```

数据包声明：

- 初始阶段；
- 阶段可见名称；
- 允许到达的相邻阶段；
- 进入和离开阶段的 `mcfunction` 回调；
- 各阶段可见的主持人和玩家面板操作。

第一里程碑持久化中的 `GamePhase` 枚举暂时作为旧存档兼容桥。它不再扩展，也不作为新游戏配置的定义来源；活动游戏和阶段真正接入时再进行一次显式、可恢复的存档 Schema 迁移。

### 5.2 状态机原则

- 阶段转换只能由服务端执行；
- 每个转换必须检查当前阶段、权限和前置条件；
- 重复请求不能造成重复转换；
- 过期界面发出的请求应被拒绝并刷新界面；
- 不依赖客户端动画结束来决定服务端阶段；
- 需要全体完成的阶段必须保留完成名单和未完成原因；
- 游戏结束条件暂不写死，由未来内容层通过安全事件请求触发。
- 所有人完成初始化或准备只会满足转换条件，不会自动转换阶段或开始游戏；
- 具体阶段定义缺失时保留原始阶段 ID，阻止不安全推进，不自动回退到默认阶段。

## 6. 主持人与管理控制

### 6.1 主持人

- 每个世界同时只有一名主持人；
- 主持人身份跨 `/reload` 持久保存；
- 世界无主持人时，任意 OP 可从图形化面板二次确认后原子认领；
- 不自动把服主、首个进入玩家或首个 OP 设置为主持人；
- 正常控制通过图形化面板完成，不要求主持人手敲命令；
- 主持人可以将权限转交给其他符合条件的玩家；
- 另一名 OP 可以在必要时接管主持人身份；
- 转交和接管均属于高风险操作，必须有明确确认与审计记录；
- 主持人默认不进入普通参与者初始化名单。
- 认领、转交或接管成功后，相关玩家的 ESC 入口与权限快照立即更新；成功者收到一次克制的 ActionBar 动画和音效反馈。

### 6.2 上下文控制台

主持人控制台不能是固定不变的按钮集合。打开时应根据当前阶段优先显示最可能需要的操作。

示例：

- `IDLE`：游戏配置、发起初始化；
- `INITIALIZING`：完成进度、未完成人员、猎人分配、锁定初始化；
- `INITIALIZATION_LOCKED`：检查角色、开放准备；
- `READY`：准备进度、未准备人员；
- `AWAITING_APPROVAL`：开局审批；
- `COUNTDOWN`：倒计时状态及取消；
- `RUNNING`：存活人数、捕获/复活状态、运行期控制；
- `ENDED`：结果与重置。

次要功能仍可进入，但首屏必须服务于当前阶段。

### 6.3 高风险操作二次确认

管理员按钮涉及高风险操作时必须二次确认。确认页不能只写“是否确认”，必须明确展示：

- 正在操作什么；
- 操作目标是谁或哪一轮游戏；
- 当前阶段；
- 将发生哪些状态变化；
- 哪些数据会保留；
- 哪些数据会清除或失效；
- 操作是否可撤销；
- 取消按钮。

适用操作至少包括：

- 发起强制初始化；
- 锁定初始化；
- 开放准备；
- 批准开局；
- 取消倒计时；
- 主持人转交或接管；
- 重置游戏；
- 恢复快照；
- 切换游戏配置；
- 其他会改变多人状态的管理操作。

确认请求使用服务端签发的一次性、短时有效令牌。令牌绑定操作者、动作、目标和状态版本；重复使用或状态已经变化时必须拒绝。

### 6.4 数据包注册的上下文操作

数据包可以注册主持人或玩家面板操作，并声明：

- 分区、排序、按钮文本、说明、图标和语义色；
- 适用阶段；
- 控制显示与可用状态的数据包 predicate；
- 用户可读的禁用原因；
- 无目标、单选或多选目标模式；
- 按身份、队伍、生存状态、三类标签和流程完成状态筛选目标；
- 明确后果的二次确认；
- 发起流程、分配身份/队伍/生存状态、转换阶段或调用受检函数。

筛选器同一数组内使用 OR，不同非空数组之间使用 AND，空数组不增加限制。流程完成筛选按当前注册的“流程 ID + 版本”判断。

`enabled_when` 存在时必须提供 `disabled_reason`。没有 `enabled_when` 时仍可提供禁用原因，用于无合格目标、选择不足等框架内置禁用状态。

2A 只注册并校验这些操作，不在界面中显示或执行；后续执行器仍必须重新验证权限、阶段、目标、predicate、确认令牌和状态版本。

## 7. 加载、重载、重置与恢复

### 7.1 `/reload`

`/reload` 绝不能清除游戏数据。

执行 `/reload` 时：

- 重新解析数据包资源；
- 对候选资源进行完整校验；
- 只有全部成功才原子替换当前资源集；
- 资源有错误时继续使用上一份有效资源；
- 向主持人显示准确的资源路径和错误原因；
- 保留主持人、玩家初始化、角色、准备、存活和捕获状态；
- 如果正在倒计时，则安全取消倒计时并保留已准备状态；
- 已经开始的动画和运镜使用启动时快照，不因资源热重载中途变形；
- 游戏运行中新增的必填字段只对下一次显式重置后创建的运行生效，不能破坏当前实例。

### 7.2 数据包成功加载提示

数据包或当前游戏配置成功加载后，应播放精致但不过度打扰的加载提示：

- 使用 ActionBar；
- 字符逐个出现，形成打字效果；
- 颜色和节奏遵循统一视觉标准；
- 搭配同步、克制的 UI 音效；
- 加载失败时不播放成功动画，应显示诊断信息；
- 普通资源重载不能因此重置游戏状态。

具体文案、逐字速度、停留时间和音效资源在视觉原型阶段确定。

### 7.3 显式重置

游戏数据只能通过明确的重置操作清除：

- 使用主持人图形界面；
- 必须经过说明后果的二次确认；
- 提供“重置本局进程”：保留活动游戏和主持人，清除玩家初始化、身份、队伍、生存状态、准备、强制流程、阶段进度、任务、事件、回顾和独占预约，然后回到活动游戏初始阶段；
- 提供“清空 Pixel TZZ 全部数据”：连主持人、活动游戏和全部 Pixel TZZ 持久状态一起清除；
- 重置前创建一份最近恢复快照；
- 防止一次点击、过期页面或重复请求误触发；
- `/reload`、服务器重启和数据包更新都不能隐式触发任何一种重置。

### 7.4 持久化与恢复快照

- 数据按世界保存；
- 使用带版本号的持久化结构；
- 玩家记录以 UUID 为主键；
- 迁移或重置前保留一份最近恢复快照；
- 迁移失败不得覆盖原始数据；
- 主持人可通过详细二次确认恢复快照；
- 第一版提供只读诊断导出；
- 第一版不提供任意数据导入或通用存档编辑器。

## 8. 玩家初始化

### 8.1 启动方式

- 初始化不会因数据包加载或玩家进入自动开始；
- 只能由主持人在允许的阶段主动发起；
- 发起前显示详细二次确认；
- 发起时按流程受众规则锁定当时在线的实际参与者；
- 名单不会因普通上线或掉线自动改变分母；
- 后来上线者显示为“未纳入”，由主持人显式补充；
- 确定退出者可由主持人二次确认后从本次事件移除。

### 8.2 初始化入口

- 玩家不能自行选择猎人、逃走者或旁观者；
- 当前游戏默认身份是逃走者；
- 通用初始化当前只包含数据包注册的教程页面与最终确认；
- 暂不注册性别、称谓或其他尚无实际用途的剧情字段；
- 旁观者无需先完成初始化，由主持人面板直接设置；
- 队伍默认也只能由主持人设置，只有数据包明确注册“允许玩家自行选队”流程时才开放。

### 8.3 强制界面

- 初始化界面在需要玩家完成时不能通过 ESC、普通关闭按钮或重复打开其他菜单绕过；
- 玩家可以在初始化流程允许的页面间导航；
- 未通过服务端校验前不能伪造“已完成”；
- 客户端异常时必须有安全错误页、重试与重新同步能力，不能把玩家永久困在黑屏；
- 强制性来自服务端阶段与完成状态，客户端重连后仍会恢复正确页面。
- 每完成一页立即保存服务端进度；
- 玩家掉线、客户端重启或服务器重启后从上次未完成页面继续；
- `/reload` 不热替换正在运行的流程；当前实例继续使用发起时冻结的定义 generation。

### 8.4 身份初始化

- “通用初始化”和“身份初始化”是两个独立流程；
- 通用教程默认只面向数据包标记为参与者的身份；当前猎人偏后台，不参加通用流程；
- 主持人在通用初始化前即可多选玩家发起猎人初始化；
- 已是逃走者的玩家可转换为猎人，已有猎人也可重新初始化；
- 二次确认后只写入待转换状态，目标完成身份流程后才原子提交正式身份；
- 旁观者转换默认二次确认后立即生效，但数据包可以为它配置流程；
- 一个活动游戏同时最多存在一个未结束的强制流程实例；
- 当前实例结束或取消前，后发流程请求应明确拒绝，不建立玩家级或全局持久队列。

### 8.5 完成与人工调整

- 主持人能随时查看初始化完成进度；
- 主持人能查看未开始、进行中和离线的未完成玩家；
- 离线且未移除者仍在分母中；
- 主持人可显式补充或移除名单成员，所有操作记录操作者、目标和时间；
- 全部完成只标记初始化已完成，不自动进入准备；
- 主持人通过详细二次确认后进入准备阶段；
- 进入准备后仍允许调整身份或队伍，但被调整玩家的准备状态失效，必须完成对应流程后重新准备。
- 流程完成记录绑定流程 ID 与版本；数据包提高版本后，旧记录保留作历史，但玩家对当前版本重新视为未完成。

## 9. 数据驱动的自定义字段

### 9.1 固定字段与配置字段

模组核心固定管理：

- UUID；
- 最近使用的玩家名；
- 主持人身份；
- 当前活动游戏和阶段 ID；
- 身份、队伍和生存状态的命名空间 ID；
- 准备；
- 在线状态与时间信息。

地图或玩法特有字段由数据包中的版本化字段 Schema 定义，不写死在核心代码中。
流程选择先写入本次流程临时数据；只有字段显式声明为玩家持久字段时才跨流程、重启和 `/reload` 保留。

### 9.2 第一版字段类型

- 布尔值；
- 单选；
- 独占单选；
- 多选；
- 整数；
- 带范围限制的整数；
- 带长度限制的短文本；
- 资源标识符。

### 9.3 字段定义能力

字段定义至少可以描述：

- 稳定字段 ID；
- 显示名称和帮助文字；
- 类型；
- 默认值；
- 是否必填；
- 可见条件；
- 适用角色；
- 适用阶段；
- 玩家是否可编辑；
- 主持人是否可编辑；
- 数字范围或选项集合；
- 文本长度限制；
- 服务端验证规则；
- 修改后是否使准备失效；
- 数据版本及迁移策略。

表达式必须是受限、可验证的数据绑定或条件表达式，不允许执行任意 Java、命令或客户端脚本。
删除字段定义时保留已有原始值并标记为未解析，不自动清除或替换。

字段 `version` 必须为正整数。迁移策略默认 `preserve`；`reset_to_default` 必须同时提供满足当前类型和约束的显式默认值。2A 只注册并校验版本和策略，实际迁移在持久字段执行器接入后完成。

### 9.4 独占单选

`exclusive_choice` 用于多名玩家不能同时占用同一选项的持久选择。模组权威管理临时预约、改选和最终锁定，客户端或数据包不能通过普通字段写入制造重复占用。

- 选项、名称、说明、图标和预览页面由数据包注册；
- 同一游戏实例、字段和选项至多一个有效持有者；
- 选择时临时预约，流程最终完成后锁定；
- 改选必须原子释放旧临时值并占用新值；
- 掉线、重启和 `/reload` 不释放；
- 重新初始化期间保留旧锁定值，新流程成功后才原子交换；
- 角色不再适用该字段时可以按字段定义释放；
- 第一用途是猎人开局前选择唯一出生点，但核心不能写死猎人或出生点语义。

出生点只表示部署位置，不表示猎人是否已经释放。等待释放、已释放和释放批次继续由数据包注册的身份、队伍、生存状态、持久字段或标签组合表达，任务结果通过受控状态变更和回调执行；模组不理解猎人箱或释放条件。

## 10. 身份、队伍、状态与猎人指定

### 10.1 三个独立维度

- `role`：主要身份，例如数据包注册的逃走者、猎人、旁观者；
- `team`：身份内部的可选分队；
- `life_state`：存活、已捕获等独立状态。

主持人是世界级控制权限，不是主要身份。被捕玩家仍保留原身份和队伍，复活只恢复生存状态。

身份和队伍的可见名、说明、TAB 前缀、颜色、标签及允许关系由数据包注册；生存状态的可见名、说明和标签也由数据包注册。模组不识别“猎人”“存活”等显示文字，也不把具体身份或生存状态写入 Java 枚举。

### 10.2 猎人指定

- 当前默认身份由游戏定义注册为逃走者；
- 主持人在通用初始化前即可单选或多选玩家发起猎人初始化；
- 不需要等待其他玩家完成通用教程；
- 指定猎人、逃走者转猎人和猎人重新初始化均使用数据包注册的流程；
- 二次确认后仅建立待转换事务，玩家完成流程后才正式提交身份；
- 目标掉线时事务和流程进度保留，重连后继续；
- 已进入准备的玩家发生身份或队伍变化时，准备状态立即失效；
- 具体身份调整按钮、筛选条件、确认文案和流程绑定由数据包注册，服务端模组重新验证。

## 11. 准备与开局审批

### 11.1 开放准备

- 初始化锁定后，由主持人确认开放准备；
- 玩家准备页面属于强制流程，不能自行关闭；
- 玩家点击准备前应看到自己的已锁定信息和必要提示；
- 正常界面中一旦准备完成，玩家不能取消；
- 只有数据包受众规则选中的实际参与者进入准备分母；
- 当前配置下猎人、旁观者和主持人不阻塞准备；
- 主持人默认不能代替玩家准备；
- 框架可允许特殊数据包显式启用“主持人强制准备”，但当前配置不启用，且操作必须二次确认并审计。

### 11.2 掉线与准备

- 准备阶段参与者掉线会清除其已准备状态；
- 重连后恢复身份和初始化数据，但不会自动恢复准备；
- 掉线造成全员准备条件不再满足时，阶段应回到实际对应的等待状态；
- 观战者掉线不影响准备。

### 11.3 全员准备后

- 全员准备不会自动开局；
- 全员完成时进入数据包注册的“等待批准”阶段；
- 必须由主持人批准；
- 主持人批准开局属于高风险操作，必须经过详细二次确认；
- 确认页明确显示参与人数、猎人人数、逃走者人数、未满足的开局前要求，以及当前版本是否启用倒计时；
- 数据包可以注册身份所需的开局前持久字段，例如猎人独占出生点；
- 任一参与者未满足其开局前要求时，服务端必须阻止批准；
- 开局批准的最终提交必须把冻结完整可达任务计划、固定本局参与者、进入起始游戏阶段和启动首个赛前环节或任务作为一次原子事务完成。

### 11.4 后续倒计时扩展（2D 未启用）

当前 2D 在主持人完成二次确认后立即原子批准，不提供倒计时配置。以下语义保留为后续扩展要求，不能据此宣称当前版本已实现倒计时：

- 后续启用时默认倒计时为 10 秒；
- 使用自定义 HUD 和 Title 风格动画；
- 文字、颜色变化和音效在所有客户端上同步；
- 倒计时完成后，服务端才原子提交开局批准事务：冻结任务计划、进入数据包注册的起始游戏阶段并启动首个赛前环节或任务；
- 参与者掉线会取消倒计时；
- 主持人掉线会取消倒计时，但保留所有准备状态；
- 主持人手动取消后回到数据包注册的“等待批准”阶段；
- `/reload` 期间安全取消倒计时并保留准备状态；
- 取消原因应清楚告知主持人和相关玩家；
- 不以某个客户端动画是否播放完成作为开局依据。

## 12. 全体选择事件与主持人进度

任何需要一组玩家全部完成的事件都使用统一进度机制，包括但不限于：

- 玩家初始化；
- 玩家准备；
- 未来任务中的强制选择。

### 12.1 主持人进度条

当前主持人专属 BossBar 显示：

```text
<事件名称>: <完成数>/<总数>
```

要求：

- 事件名称、数字和状态使用统一且有语义的配色；
- 进度变化平滑；
- 正常、等待、即将完成、阻塞等状态可以有不同视觉反馈；
- 分母严格来自本流程锁定的实际参与者，不统计被受众规则排除的猎人、主持人或旁观者；
- 上下线不自动改变分母，离线且未移除者仍计入未完成；
- 名单增删后按主持人确认的结果更新；
- 玩家端不显示主持人专属管理信息。

流程可配置 BossBar 名称模板、原版颜色、原版分段样式、优先级和完成反馈；名称模板必须包含事件名、完成数和总数占位符，完成反馈可以配置文本、颜色、停留 Tick 与声音 ID。多个受跟踪流程可同时显示。未来自定义 HUD 可以增强节目效果，但不能取消这里已经确认的主持人 BossBar。

### 12.2 未完成人员

主持人控制台提供：

```text
查看未完成人员（n）
```

进入后显示：

- 玩家头像与名称；
- 在线/离线；
- 当前完成状态；
- 未开始、进行中或离线分类；
- 缺少的具体字段、节点或步骤；
- 最后状态时间；
- 当前是否阻塞全体进度。

离线玩家的信息来自持久化记录，不依赖其当前在线。

## 13. 上下线与玩家记录

### 13.1 UUID 玩家记录

每名相关玩家持久化保存：

- UUID；
- 最近使用的玩家名；
- 参与或观战选择；
- 角色；
- 初始化字段；
- 准备状态；
- 存活、捕获和复活状态；
- 在线/离线状态；
- 相关状态更新时间；
- 当前轮次标识。

### 13.2 掉线提醒规则

| 玩家状态 | 掉线处理 |
|---|---|
| 尚未初始化 | 不提醒 |
| 观战者 | 不提醒 |
| 已初始化参与者 | 提醒主持人 |
| 已准备参与者 | 提醒主持人并清除准备 |
| 倒计时中的参与者 | 取消倒计时 |
| 游戏中存活逃走者 | 记录并提醒，不自动判定被捕 |
| 主持人 | 取消倒计时；其他阶段保留游戏数据 |

重新连接时恢复其身份、初始化字段、角色和运行状态。被掉线规则明确清除的准备状态不恢复。

## 14. 捕获、死亡旁观与复活

### 14.1 捕获判定

- 正在游戏中的存活逃走者遭遇任何致死结果，都算被捕；
- 不区分猎人攻击、环境伤害、指令伤害或其他死亡原因；
- 猎人或观战者的死亡不套用“逃走者被捕”语义；
- 对同一名玩家的重复致死事件只能成功处理一次；
- 捕获状态流转为：

```text
ALIVE → CAPTURING → CAPTURED
```

### 14.2 不进行原版真实死亡

致死结果由模组在安全时机拦截：

- 不进入原版死亡界面；
- 不掉落物品；
- 不丢失经验；
- 不执行原版重生传送；
- 屏蔽对应的原版死亡提示；
- 捕获动画期间暂时冻结并保护玩家；
- 动画结束后进入被捕后的旁观状态；
- 不依赖死亡后再把玩家传回原位置。

服务端必须防止其他模组、重复伤害或网络重试造成重复捕获和重复广播。

### 14.3 捕获消息

正常聊天历史中依次记录：

```text
<玩家名> 被猎人捉捕！
还有 <数量> 名逃走者仍在逃亡。
```

要求：

- 第一行使用深红色；
- 第二行突出剩余数量；
- 剩余数量只统计当前存活逃走者；
- 已捕逃走者仍属于逃走者角色，但不计入存活数量；
- 消息可以使用动态聊天动画，但最终内容必须留在普通聊天历史中。

### 14.4 捕获镜头

默认捕获镜头约 2.5 秒：

1. 保留玩家身体在捕获点；
2. 受害者视角平滑切换为第三人称；
3. 镜头看向自身捕获位置；
4. 镜头向后、向上缓慢拉远；
5. 结束时平滑交接到被捕后的旁观视角。

碰撞与异常空间处理：

- 使用多射线或连续碰撞检测避免镜头穿墙；
- 后方受阻时尝试替代角度；
- 空间狭窄时缩短距离；
- 接近虚空或找不到安全机位时使用短拉远、FOV 变化或淡出；
- 不能把镜头卡进方块；
- 断线、重载或动画取消时恢复正常相机状态；
- 开启“减少动态效果”时使用约 0.5 秒的简化过渡。

### 14.5 复活

- 未来任务可以请求复活已捕逃走者；
- 复活将 `CAPTURED` 恢复为 `ALIVE`；
- 玩家角色始终保持逃走者；
- 恢复可游玩状态、TAB 状态及存活人数；
- 对已经存活的玩家重复复活不得产生副作用；
- 复活细节通过受控模组接口完成，数据包不能直接篡改核心状态。

### 14.6 零存活者

存活逃走者变为 0 时，模组发出标准事件钩子。第一版核心不直接写死游戏结束，因为最终结束规则仍取决于未来主线和任务设计。

## 15. TAB 玩家列表

TAB 样式必须来自数据包定义，不根据“猎人”“逃走者”、固定标签或 Java 枚举推断。身份、队伍和生存状态可以分别注册前缀、名称颜色、排序优先级及覆盖方式，按下列顺序合成：

```text
role → team → life_state → host system override
```

要求：

- 前缀显示在玩家名称前；
- 主持人是系统权限，始终以金色 `[主持人]` 最高优先级显示；
- 身份可以绑定初始化流程，只有本次身份提交带有匹配流程 ID、版本和成功实例凭据后才公开身份前缀、颜色和身份排序；更早的历史完成不能绕过本次重新初始化；
- 没有初始化流程的身份可以立即公开；
- 未公开身份不添加前缀、不修改颜色，也不打乱玩家的初始自然顺序；
- 队伍和生存状态可以补充或覆盖身份样式；
- 角色和存活状态变化后及时同步；
- 复活后按保留的身份、队伍和新的生存状态重新合成样式；
- 不能只靠颜色传达信息，前缀文本必须保留；
- 不修改玩家 UUID 或真实名称；
- 与其他模组的 TAB 扩展发生冲突时应提供诊断和可配置降级方式。

第一套正式数据包推荐呈现主持人、猎人、逃走者、旁观者从上到下排序，猎人红色、逃走者绿色、旁观者灰色；这是内容配置，不是核心写死规则。

## 16. UI 视觉与交互标准

### 16.1 风格

总体风格为克制、清晰的“电视节目控制台”：

- 有节目感；
- 信息层级明确；
- 颜色和谐；
- 不使用无意义的彩虹色堆叠；
- 动画精致但不拖慢操作；
- 玩家端更沉浸，主持人端更强调状态和风险。

### 16.2 核心色板

| 语义 | 颜色 |
|---|---|
| 品牌金 | `#F4C95D` |
| 信息青 | `#64D8E8` |
| 主文字 | `#F2F2F2` |
| 次要文字 | `#A7ADB7` |
| 成功 | `#65D68A` |
| 警告 | `#F6B94A` |
| 危险 | `#E94F64` |
| 捕获 | 深红色，最终色值在视觉原型中确定 |

颜色必须按语义使用，同一状态在 GUI、HUD、Title、聊天和提示音中保持一致。

### 16.3 动画标准

适合覆写的区域应提供比原版更细致的动画：

- 字符逐个出现；
- 白色向红色等逐字或逐区域颜色填充；
- 连续渐变；
- 淡入淡出；
- 平滑尺寸和位置变化；
- 进度条平滑过渡；
- Title 与 HUD 的同步节奏；
- 动画关键点配合声音。

动画速度应连续、可调整，不使用生硬的少数速度档位。任何动画都不能延迟服务端真实状态或阻碍紧急操作。

### 16.4 ESC 入口

- 自定义系统在 ESC 中注册稳定入口；
- 普通状态下打开上下文相关的玩家页面；
- 主持人打开上下文相关的控制台；
- 被强制进行初始化或准备时，ESC 应回到当前强制页面，而不是允许退出流程；
- 原版必要按钮仍应可用，不能破坏正常退出游戏、辅助功能和错误恢复。

### 16.5 动态页面

页面必须支持：

- 服务端状态实时更新；
- 动态文字；
- 动态按钮标签；
- 按状态显示或隐藏；
- 不可用状态及明确原因；
- 玩家头像、图标和状态；
- 可滚动玩家列表；
- 键盘导航；
- 不同 GUI 缩放和窗口尺寸；
- 加载、空状态、错误和重连状态；
- 主持人/玩家/观战者不同上下文。

## 17. 数据驱动布局系统

### 17.1 目标

自定义 GUI 不只用于开局面板，还要能复用于后续任务、游戏配置和新版本创意。因此页面不能全部写死在 Java 中。

### 17.2 职责分工

Java 提供安全组件、布局引擎、数据绑定、事件请求和渲染能力；页面通过数据资源描述：

- 布局；
- 样式；
- 文字；
- 动画；
- 数据绑定；
- 可见条件；
- 按钮动作 ID；
- 响应式规则。

数据资源不能包含任意脚本或任意 Java 调用。

### 17.3 布局能力

第一版布局系统目标支持：

- Row；
- Column；
- Grid；
- Flow；
- Scroll；
- Card；
- Overlay；
- 最小/最大尺寸；
- 固定、内容、自适应和比例尺寸；
- 边距、间距、对齐；
- 锚点；
- 响应式断点或约束；
- 长列表虚拟化。

Split 由 Row/Column 加权重表达，垂直堆叠使用 Column，层叠使用 Overlay。第一版不建设含义重叠的 Split 或 Stack 运行时；未来确需简写时只能在编译阶段降低为上述核心布局。

### 17.4 页面扩展

- 核心页面和任务页面使用同一文档格式；
- 数据包可以添加或覆盖被允许的页面资源；
- 所有页面在启用前必须通过 Schema、资源引用和复杂度校验；
- 服务端只接受注册过且在当前状态允许的动作 ID；
- 数据包页面不能绕过服务端权限；
- 第一版提供预览器和布局检查器；
- 第一版不提供拖拽式页面编辑器。

## 18. 动态聊天文本

### 18.1 核心行为

动态文本必须是真正进入原版聊天历史的可更新消息，不是盖在聊天框上方的独立假聊天层。

流程：

1. 服务端发送最终文本组件、稳定唯一 ID 和动画规格；
2. 客户端在聊天历史中插入一个逻辑条目；
3. 动画帧持续原地更新这个条目；
4. 动画结束后最终文本保留在历史中。

### 18.2 与正常聊天共存

- 只有显式指定为动态消息的文本才播放动画；
- 普通系统消息按普通方式显示；
- 不修改签名玩家聊天；
- 动画期间玩家发言会正常把动态消息向上顶；
- 被顶上去不会中断动画；
- 即使条目已经滚出可见区域，动画状态仍可正确完成；
- 多条动态消息可以独立同时播放；
- 打开历史记录时看到的是该条目的当前帧或最终结果；
- 客户端重连不要求重播已经结束的动画，但最终重要状态由服务端当前界面体现。

### 18.3 第一版动画能力

- 多行文本；
- 打字机；
- 颜色逐字填充；
- 颜色渐变；
- 透明度变化；
- 分段延时；
- 同步字符音；
- 开始、关键帧和结束音；
- 可跳过或瞬时完成的无动画模式。

讲述人只朗读稳定的最终文本一次，不朗读每个动画帧。

### 18.4 容量边界

- 每名客户端同时运行的动态消息数量有上限；
- 单条消息字符数、行数和动画时长有上限；
- 超过限制时直接显示最终文本；
- 资源缺失时使用默认样式和声音；
- 动画不进行每 Tick 全历史扫描。

## 21. 音效与资源资产

### 21.1 音效原则

- 音效与视觉状态使用统一语义；
- 打字音不能对每个字符都制造刺耳噪声，应支持节流或按节奏采样；
- 关键确认、警告、危险、成功和倒计时使用不同声音语言；
- 客户端动画音效与动画时间轴同步；
- 服务端关键事件仍有稳定时间基准；
- 音效缺失不能阻断功能。

### 21.2 资产策略

原型阶段：

- 优先使用合适的原版声音；
- 用资源 ID 引用，不把文件路径写死在代码中。

正式阶段：

- 优先制作原创合成 UI 音效包；
- 如果必须使用外部素材，逐项记录来源、作者、许可证、是否可修改和是否要求署名；
- 项目保留许可证清单和 notices；
- 未确认授权的素材不得进入仓库和发布包。

最终音效来源以后单独研究，目前不提前锁定。

## 22. 游戏配置（Game Profile）

同一个核心模组支持可替换游戏配置。每个配置可以定义：

- 稳定 ID；
- 显示名称；
- 配置版本；
- 所需模组 API 版本；
- 主题；
- 初始化字段；
- 角色要求；
- 倒计时及规则参数；
- 页面；
- HUD；
- 动态消息；
- 运镜；
- 音效；
- 单任务时间线入口、有限任务 DAG 与双 Tick 计时规则；
- 任务、结果、间隔、事件、统计与赛后回顾；
- 开局前必填字段要求；
- 数据包事件钩子；
- 资源依赖。

规则：

- 每个世界同一时间只有一个活动配置；
- 只能在 `IDLE` 阶段切换；
- 切换前二次确认；
- 配置不兼容或校验失败时保留当前有效配置；
- 未来“全员逃走中 2.0”优先作为新内容配置，而不是复制核心模组。

### 22.1 单任务时间线

- 一个活动游戏同时只有一个任务或赛前环节；
- 任务路线必须是有限有向无环图，不允许循环或跳过；
- 赛前环节与主任务使用同一框架，但可以不计正式游戏时间；
- 当前环节时间与正式游戏时间均使用有效服务器 Tick；
- 服务器停机和主持人主动暂停期间不流逝，`/reload` 不暂停；
- 每个任务最终只冻结一个全局结果，由数据包通过受控接口提交；
- 结果原子决定下一任务、间隔和阶段转换；
- 到时后数据包没有提交结果时停留在结算异常，模组不能猜测结果；
- 间隔结束后默认自动进入下一任务，主持人可二次确认延长或提前结束；
- 最终任务经过可配置最终间隔后进入数据包注册的结束阶段；
- 主持人可查看完整时间线，普通玩家默认不可查看实时时间线；
- 赛后回顾只显示本局实际发生的任务、事件和统计，并保留到显式重置；
- 已完成游戏存在时不能自动覆盖或直接开始第二局。

## 24. 网络、安全与审计

### 24.1 网络

- 使用明确版本的客户端/服务端协议；
- 登录或进入世界时完成能力握手；
- 客户端缺失、版本不匹配或资源能力不足时给出明确错误；
- 同步采用状态快照加增量更新；
- 不每 Tick 广播完整玩家列表；
- 页面打开后订阅其需要的数据，关闭后释放；
- 动画和运镜尽量在客户端执行，服务端只同步开始时间和权威事件。

### 24.2 信任边界

- 网络请求使用有类型的动作；
- 校验操作者、权限、阶段、目标、参数和资源 ID；
- 高风险动作使用一次性确认令牌；
- 拒绝过期、重放和状态版本不匹配的请求；
- 限制单包大小、字符串长度、列表长度和调用频率；
- 限制 UI 文档节点数、嵌套深度和表达式复杂度；
- 不接受客户端提交的“我是猎人”“我已准备”等最终状态。

### 24.3 审计

至少记录：

- 时间；
- 操作者 UUID 和名称；
- 操作类型；
- 目标；
- 操作前后阶段；
- 成功或拒绝；
- 拒绝原因；
- 相关轮次 ID。

普通字符动画帧、HUD 插值等纯客户端行为不进入服务端审计。

15. 只有有效且非空的新定义 generation 才播放加载成功动画；
16. 限制 JSON 深度为 `64`、单文件字符数为 `262144`、定义总字符数为 `8388608`；诊断详情只保留并逐条输出前 `100` 条，同时准确累计并显示总数；
17. 提供 `23` 文件、`15` 项定义的示例数据包、格式文档和不启动世界即可运行的自检。

2A 明确不执行流程或面板操作，不渲染数据包页面、图标或 BossBar，也不修改玩家身份、队伍、生存状态、阶段、字段或准备状态。完整格式见 `docs/DATA-PACK-API-2A.md`。

## 28B. 第二里程碑 2B：数据驱动页面框架

10. 动画与音效使用受限声明式事件时间线，并支持减少动态效果和声音限流；
11. 页面按钮只提交 Local、Flow 或 Registered 三类有类型意图，2B 不执行真实操作；
12. 页面是否强制由服务端实例决定，强制页面仍保留设置、辅助功能、错误恢复和断开连接；

23. 当前基础示例包含 `31` 个文件和 `23` 项 Pixel TZZ 定义。

完整格式见 `docs/DATA-PACK-UI-2B.md`，实施与验收边界见 `docs/MILESTONE-2B-PLAN.md`。

## 29. 验收总原则

每项功能同时满足以下条件才算完成：

1. **行为正确**：服务端状态符合本文档；
2. **异常安全**：掉线、重载、重复请求和资源错误不会破坏数据；
3. **界面一致**：颜色、文字、动画和声音遵循统一标准；
4. **权限可靠**：客户端或数据包不能绕过服务端；
5. **性能有界**：人数、节点、消息和动画量均有明确上限；
6. **可扩展但不过度设计**：地图和任务可通过内容层扩展，核心不建设无关通用系统；
7. **可验证**：自动检查与实际进世界测试均有记录；
8. **不擅自定案**：地图、任务、主线和未确定资产继续保持可替换。
