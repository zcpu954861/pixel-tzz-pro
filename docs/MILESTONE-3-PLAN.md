## 0. 文档职责

本文记录第二里程碑 2A～2D 收口后，Pixel-Tzz-Pro V3 的产品分段、统一质量基线以及已经由用户明确确认的玩家侧要求。

本文不是数据包格式文档，也不是已经实现的功能清单。后续只有在对应分段的功能细节逐项确认后，才能补充 Schema、协议、状态迁移、测试计划和完成定义。

总需求仍以 [`REQUIREMENTS.md`](REQUIREMENTS.md) 为准。V3 后续形成稳定 API 时，应另建对应的数据包 API 文档，不能让实现者只依赖本文中的示意字段。

## 1. V3 定位

第一里程碑完成工程、握手、持久化、加载反馈和 ESC 入口。第二里程碑 2A～2D 已经完成：

- 数据包注册与严格校验；
- 数据驱动页面、布局、主题、组件、动画和声音声明；
- 主持人控制台、强制流程、身份事务、BossBar 和二次确认；
- 逐玩家准备、开局审批、单活动任务时间线、事件、统计、回顾、独占选择和两级重置。

现有管理侧已经功能强大，并经过连续多轮多人实机验收与视觉微调。V3 不再以扩充管理功能为重心，而是补齐玩家持续可见、可感知的正式游戏体验：

- 玩家终端；
- 动态文本；
- 自定义 HUD；
- 通用运镜；
- 捕获、死亡旁观和复活；
- 统一声音、辅助功能、性能和兼容收口。

玩家侧的信息架构通常比主持人侧简单，因为普通玩家不负责全局配置、权限裁决和多人状态管理。简单不等于粗糙。主持人控制台现有水准是 V3 的最低质量基线；玩家侧因在整局游戏中持续暴露，应在层级、动画、声音、连贯性和异常恢复上达到相同或更高完成度。

## 3. V3 统一质量基线

以下要求一次确认后适用于全部玩家侧页面、HUD、动态文本和演出，不需要用户在每个页面重复强调。

### 3.1 视觉与组件

- 沿用 2B～2D 已形成的主题、语义色、字体层级、按钮、头像和页面描边语言；
- 管理侧现有完成度是玩家侧的最低标准，不能回退到早期占位式 UI；
- 中文是主要信息，英文只能作弱化衬托；
- `『』` 用于正式注册名称，`「」` 用于当前对象、当前选项和具体结果；
- 普通按钮、连续正文和英文副标题不得滥用上述符号；
- 玩家头像必须使用真实皮肤基础层和帽子层；离线时只对头像进行灰度处理；
- 颜色不是唯一状态载体，必须保留文本、图标、形状或动画差异；
- 不使用未经统一风格化的原版输入框、按钮或列表作为正式玩家页面。

### 3.2 交互与动画

- 普通、悬停、按下、禁用、等待、成功和失败状态均有明确视觉反馈；
- 悬停不移动控件本体，不周期性重播进入动画，不播放无必要的悬停声音；
- 页面进入、页面间跳转、返回上一级和关闭到游戏必须形成完整过渡；
- 服务端通信不插入风格不一致的中间等待页；
- 短暂同步只锁定相关操作或显示局部加载，不使其他控件闪烁、重建或丢失焦点；
- 普通后台刷新保持静默；需要显示同步状态时复用统一的右上角徽标；
- 动画和声音不能抢播、重叠或掩盖上一条仍需阅读的内容；
- 玩家可见动画不得拖延、伪造或覆盖服务端权威状态。

### 3.3 响应式与异常恢复

- 不同 GUI 缩放、窗口尺寸和长文本下，核心操作始终可达；
- 空间不足时先压缩次要信息，再使用明确的分区滚动；
- 滚动范围不能超过实际内容，也不能裁切标题、必填提示或底部操作；
- 页面打开期间服务端状态变化应尽量原地更新；
- 当前页面不再适用时，使用正常切换动画进入新的权威页面；
- 掉线、重连、资源错误和页面失效时不能卡死、误操作或泄露后台诊断；
- 视觉、声音、多人同步和手感必须经过真实客户端验收，自动检查不能代替。

## 4. V3 的数据驱动原则

V3 的核心原则是：

> 模组提供能力、权威数据源、安全组件和受控执行器；数据包独立注册每一项玩家可见功能。

“数据驱动”不能退化为模组固定生成一张任务卡，再允许数据包替换几个字符串。每一项可见能力必须能够独立启用、关闭、布置和绑定：

- 页面；
- 页面入口与路由；
- 文本；
- 图像与头像；
- 状态；
- 时间；
- 进度；
- 统计；
- 个人数据；
- 历史事件；
- 按钮；
- 动画；
- 声音；
- HUD 元素；
- 动态消息；
- 运镜和捕获演出。

缺少某项配置时就不显示该功能，模组不能擅自补出一套正式内容。配置缺失、资源错误或协议异常时可以进入内置安全页，但安全页只用于恢复和诊断，不算正式玩家界面。

全自由注册不等于任意客户端脚本：

- 所有资源经过严格 Schema、引用和复杂度校验；
- 客户端只能提交有类型意图；
- 服务端重新验证玩家、阶段、任务、受众、目标、参数、次数和冷却；
- 未授权数据不下发客户端；
- 数据包函数可以修改 Minecraft 世界，但不能直接改写模组权威状态。

## 5. 单 Game Profile 范围

V3 不建设多 Game Profile 同时加载后的选择与切换系统。

- 一套实际运行的正式数据包资源集合只注册一个 Game Profile；
- 没有游戏定义时显示明确诊断；
- 同时出现多个游戏定义时视为内容配置冲突，不能让客户端选择或静默猜测；
- 不提供首次配置选择页；
- 不提供运行中或 `IDLE` 阶段的配置切换页；
- 未来“全员逃走中 2.0”通过更换数据包、资源包或世界内容实现，不要求一个世界同时携带多套可切换游戏。

这项范围缩减不改变 Game Profile 作为单套游戏定义根节点的作用。

## 6. V3A：玩家终端

### 6.1 入口与权限

- 主持人继续进入主持人控制台；
- 所有非主持人玩家进入玩家终端；
- 非主持人 OP 不再拥有独立管理员控制台；
- 非主持人 OP 在普通玩家终端基础上，只额外获得一个低优先级主持人操作：无主持人时为“认领主持人”，已有其他主持人时为“接管主持人”；
- 主持人操作按钮不能抢占当前任务、个人状态或历史事件的视觉焦点；
- 认领与接管都使用服务端权限检查、详细二次确认和审计；接管再执行原子主持人替换；
- 非主持人 OP 在服务端同样不能取得完整主持人 `ConsoleSnapshot`；
- 非主持人 OP 同样不能请求主持人专用页面预览目录或页面文档；
- 数据包不能伪造、替换或隐藏该系统主持人按钮。

### 6.2 强制流程与普通终端

- 玩家处于服务端强制流程时已经被锁定在强制页面，不进入玩家终端；
- 此时 ESC 入口只负责返回当前强制页面；
- 玩家终端不重复显示“必须完成的流程”、节点或进度；
- 只有数据包注册的强制流程可以锁定页面；
- 普通玩家终端永远不因任务、事件、身份变化而强制弹出，并可随时关闭。

### 6.3 终端职责

玩家终端不是缩小版主持人控制台，也不是固定按钮合集。它主要承载：

- 当前任务的数据包玩家视图；
- 玩家个人状态和经授权的个人字段；
- 已经发生且允许玩家回顾的历史事件；
- 数据包注册的详情、帮助和任务相关页面；
- 设置与安全恢复入口；
- 非主持人 OP 的次要认领/接管按钮。

玩家终端不承载：

- 主持人全局配置；
- 完整玩家名单；
- 未公开任务路线或未来节点；
- 隐藏结果与后台分支；
- 回调审计和内部注册 ID；
- 普通玩家无权读取的其他玩家数据。

### 6.4 页面入口路由

玩家终端打开哪一页也由数据包注册。当前确认的选择层级为：

1. 强制流程存在时不进入终端，返回强制页；
2. 当前任务注册了适用于该玩家的终端页时，使用任务专属页面；
3. 否则按阶段、身份、队伍、生存状态及受限条件选择上下文页面；
4. 没有更具体匹配时使用游戏默认玩家页面；
5. 配置缺失或错误时进入内置安全页。

每条路由应独立声明：

- 页面 ID；
- 受众；
- 阶段和任务条件；
- 受限可见表达式；
- 明确优先级。

候选冲突必须在加载或服务端投影阶段诊断，客户端不能自行猜测。

### 6.5 页面内部导航

- 每个按钮独立注册打开的页面；
- 按钮可以传递受限、结构化上下文；
- 页面栈、返回上一级、转场和错误恢复由模组负责；
- 数据包决定页面之间的关系，不在 Java 中写死任务说明页、历史页和详情页层级；
- 历史记录可以打开该事件注册的可选详情页；
- 详情按钮只上送当前投影条目的有界记录键；目标页、正文和页面栈均由服务端按当前查看者与活动局冻结定义重新解析；
- 当前页面条件失效时，模组根据服务端最新路由进入新的合法页面。

## 7. V3A：当前任务玩家视图

### 7.1 不提供固定任务卡

当前任务是游戏进行中玩家终端的常见主体，但模组不固定生成包含全部字段的“标准任务卡”。

数据包应能分别决定：

- 是否公开当前任务；
- 向哪些身份、队伍或玩家公开；
- 任务名称；
- 目标摘要；
- 详细规则；
- 当前状态；
- 已进行时间；
- 剩余时间；
- 数字进度；
- 进度条或自定义进度组件；
- 公共统计；
- 当前玩家自己的目标、进度和结果；
- 可选详情页；
- 可选任务操作按钮；
- 每项内容的布局、样式、排序和可见条件。

所有功能是独立配置项。任务可以只显示一个名称，也可以提供完整的任务面板；未注册的部分不显示。

### 7.2 受众与信息安全

- 同一任务可以为逃走者、猎人、旁观者或其他数据包身份注册完全不同的页面；
- 时间、公共统计和其他玩家进度不默认公开；
- 没有为当前玩家注册任务视图时，不发送隐藏任务事实；
- 不显示未来任务、未触发节点、隐藏分支、后台结果或内部 ID；
- HUD 只显示数据包注册的精简内容，玩家终端可以承载完整说明；
- 任务进度、状态和暂停变化在打开的页面内自动更新，不要求玩家手动刷新。

### 7.3 任务结束

- 任务结束后不再作为当前任务显示；
- 页面根据最新服务端路由平滑切换；
- 任务、结果或任务内事件是否进入玩家历史，由独立的回顾配置决定；
- 任务结束本身不强制打开玩家终端。

## 8. V3A：玩家历史事件

### 8.1 两级开关

玩家历史使用两级配置：

1. Game Profile 总开关决定本局是否启用玩家侧事件回顾；
2. 每类事件独立决定是否允许进入玩家历史。

总开关关闭时，玩家终端不存在历史区域。单条事件未显式允许时默认不向玩家公开。

### 8.2 事件事实与玩家回顾分离

- 模组可以保留完整权威事件事实，用于主持人审计、恢复和受控回顾；
- 数据包单独定义玩家能否查看、何时查看、哪些玩家能查看以及具体看到什么；
- 服务端只向查看者发送已经裁剪的玩家版本；
- 不能把完整后台事件发给客户端后仅靠界面隐藏；
- 未来任务、未发生事件、隐藏路线和未公开结果不能进入玩家历史。

### 8.3 单条事件的独立配置

每种可回顾事件应能分别声明：

- 是否可回顾；
- 公开时机，例如发生后、任务结束后或整局结束后；
- 可见受众；
- 历史标题；
- 一行摘要；
- 图标、语义色和事件类别；
- 是否显示游戏内触发时间；
- 是否显示所属任务；
- 是否显示触发者；
- 是否显示目标玩家；
- 可以公开的结果与任务统计；
- 与查看者有关的个人结果；
- 可选详细内容；
- 可选详情页。

任意事件参数保留给后续接口版本。V3A 不持久化或投影它们，`player_history.parameters` 只能省略或为空数组，非空声明必须在编译期失败，不能出现“配置有效但静默无效果”。

详情页采用独立 `history_detail` 动作，不复用任意 `open_page` 参数。该动作只允许位于绑定 `history.items` 的 Repeat 模板中；客户端不能选择页面 ID 或提交事件 JSON。Page Frame 保存服务端解析后的记录引用，详情只读取同策略裁剪的 `detail.*`；授权丢失时只保留 `detail.exists: false`，返回恢复原列表。

实时广播文案与回顾文案分开注册。实时消息可以强调节目效果，回顾内容应稳定、完整、易读。

### 8.4 阅读体验

- 普通记录以“时间 + 标题 + 一行摘要”为主；
- 复杂记录才提供可选详情，不强制每条事件独占页面；
- 回顾时直接显示稳定正文，不重新播放打字音和强动画；
- 新记录加入时可以按数据包配置进行一次克制的高亮或滑入；
- 已发生的回顾基于当时冻结事实，不因后续 `/reload` 被改写；
- 历史按权威游戏时间排序，并保持容量有界。
- 活动局详情导航与列表一样使用开局冻结定义；live `/reload` 编译失败不能使活动局退回新定义或泄露旧记录。

## 9. V3A：玩家个人数据

模组向数据包提供可选、受控的数据源：

- 身份；
- 队伍；
- 生存状态；
- 初始化状态；
- 准备状态；
- 数据包注册的个人字段；
- 当前任务中的个人进度和结果；
- 独占选择，例如猎人出生点。

每一项独立配置：

- 是否允许本人读取；
- 在哪些阶段或任务可见；
- 对哪些身份、队伍或生存状态可见；
- 显示名称和格式；
- 是否允许用于玩家终端；
- 是否允许用于 HUD；
- 是否允许用于动态消息；
- 是否隐藏、模糊或替换为自定义文案。

玩家终端不固定生成“个人资料卡”。数据包页面自行决定使用哪些数据、怎样排版。未经授权的数据不进入客户端绑定上下文。

## 10. V3A：玩家按钮与注册函数

### 10.1 页面按钮

玩家页面按钮可以：

- 进行本地页面导航；
- 打开数据包注册页面；
- 提交数据包注册的有类型操作；
- 请求服务端执行注册函数。

客户端只发送页面、按钮和操作意图，不能直接提交“操作已经成功”或任意函数 ID。

### 10.2 注册函数操作

数据包可以为玩家按钮注册 `mcfunction`，用于装置、门、实体、粒子、声音、地图机关和其他世界内容。

每个函数操作应独立声明：

- 稳定操作 ID；
- 函数 ID；
- 允许受众；
- 允许阶段、任务和任务状态；
- 可选 predicate；
- 每次、每玩家或全局使用次数；
- 冷却；
- 是否需要额外确认；
- 函数执行上下文；
- 成功、拒绝和异常反馈；
- 审计策略。

服务端执行顺序：

1. 接收按钮意图；
2. 校验页面实例、玩家、任务、身份、条件、次数、冷却和请求防重放；
3. 解析当前注册函数；
4. 使用注册的安全上下文执行；
5. 记录审计及幂等结果；
6. 只更新真正变化的页面或 HUD 数据。

次数和冷却使用主世界持久化 `gameTime`，必须跨服务器重启保持；不能用进程生命周期内的 `server.getTickCount()` 重置。

可支持的函数上下文至少预留：

- 以点击玩家为 `@s` 并在玩家位置执行；
- 以服务器身份执行；
- 以任务注册的位置或实体作为上下文执行。

函数可以修改 Minecraft 世界，但不能直接写模组持久化文件，也不能绕过模组接口宣称任务结果、事件、统计、捕获、复活、身份或准备已经成功。

## 11. V3A：实时更新与画面控制

- 普通玩家终端不自动弹出；
- 任务开始、任务结束、事件、身份和状态变化使用 HUD、动态文本或声音提醒；
- 终端打开期间数据尽量原地更新，不重建整页；
- 路由发生真实变化时才播放一次页面切换；
- 捕获或紧急运镜需要画面控制权时，可以安全关闭普通玩家终端并进入演出；
- 强制流程不能被普通玩家演出随意中止，必须使用专门的服务端冲突规则；
- 页面关闭、演出开始和 HUD 提示之间必须有明确时序，不能在关闭动画后方才延迟出现关键界面。

## 12. V3B：已确认的动态文字演出边界

V3B 采用“先注册、后调用”：

- 一个稳定演出 ID 可以打包多个 Chat、Title、Subtitle、ActionBar、声音和服务端回调；
- 各内容可以同步或按时间线播放，并独立配置受众、动画、取值、优先级和降级；
- Chat 真正进入原版历史，普通 `tellraw`、系统消息和签名玩家聊天保持原行为；
- 动态字段支持原版富文本、可信 Score、NBT/Data、Selector、任务和个人字段；
- 字段可在内容显示时、首个动态字段前或每个字段播放前锁定；
- 服务端权威验证 ID、目标、参数、受众、条件、上下文和函数回调；
- 客户端只接收当前玩家获准播放的最小演出包；
- 重复、并发、暂停、补全、取消、掉线、Reload、重启和资源异常都有明确策略；
- 玩家可以降低动态强度或补全获准消息，但不能隐藏最终内容或延迟服务端流程；
- 主持人拥有默认无副作用的预览和诊断入口；
- 现有模组自有 Subtitle 与提示迁移到统一调度器，不保留第二套动画状态机。

完整产品语义、默认值、实施分段和完成定义见
[`MILESTONE-3B-PLAN.md`](MILESTONE-3B-PLAN.md)。已经冻结的 JSON Schema、命令拼写、协议、
状态迁移和示例见 [`DATA-PACK-MESSAGE-API-3B.md`](DATA-PACK-MESSAGE-API-3B.md)，不能只依赖
总体计划中的示意字段。

## 13. V3C：已确认的 HUD 与开局倒计时边界

V3C 采用“一个玩家、一个常驻信息位置”的原则：

- 数据包注册 HUD 组件、根布局、路由配置和倒计时；模组不硬编码标准任务卡；
- 常驻 HUD 默认锚定右下角安全区域，底边稳定、内容向上生长，不允许组件各自在屏幕上漂浮；
- 当前任务、阶段、身份、队伍和状态只能选出一个获胜根布局，不把多个根布局自动拼接；
- 倒计时是唯一允许临时占用中央画面的 V3C 表现；普通临时提醒继续由 V3B 负责；
- 服务端对根布局、组件、字段和实时上下文逐层求受众交集，只下发当前玩家获准看到的最终投影；
- 玩家可以在数据包许可范围内移动、缩放、调节透明度、隐藏、紧凑或重排整个信息坞；
- HUD 避让原版热键栏、ActionBar、声音字幕和客户端声明的其他模组排除区域；
- 正常后台刷新不闪烁、不重建、不重播进入动画，计时器根据服务端锚点在客户端平滑插值；
- 开局审批后先运行正式倒计时，倒计时结束后才进入热身；倒计时与热身均不计入全局游戏时长；
- 未注册倒计时的旧数据包保持 2D 的立即开局语义；必需但无效的倒计时阻止主持人批准；
- 倒计时不能跳过或快进，主持人只能通过绑定实例和状态版本的二次确认取消；
- `/reload` 保留正在运行的冻结倒计时，服务器重启恢复后先进入等待，不把离线时间计入倒计时；
- 倒计时限制默认冻结参与者移动、攻击、交互和物品操作并提供临时伤害免疫，但不锁定镜头、聊天或 ESC；
- 生命周期回调只在服务端执行，并由账本保证至多一次；HUD 渲染和客户端设置永不执行函数。

完整产品语义、视觉线框、默认值和实施分段见
[`MILESTONE-3C-PLAN.md`](MILESTONE-3C-PLAN.md)。资源路径、Schema、路由、组件、数据绑定、
倒计时状态与示例见 [`DATA-PACK-HUD-COUNTDOWN-API-3C.md`](DATA-PACK-HUD-COUNTDOWN-API-3C.md)。

## 14. V3A 完成定义

V3A 只有同时满足以下条件才能进入实机验收：

1. 玩家终端入口、页面路由和页面导航完全数据驱动；
2. 强制流程与普通终端的关闭、ESC 和画面控制边界明确；
3. 非主持人 OP 只获得受控接管按钮，不获得主持人视图；
4. 当前任务没有固定任务卡，每一项可见功能独立注册；
5. 玩家历史具备总开关、逐事件公开、内容、受众和时机裁剪；
6. 玩家个人数据逐项声明本人可见性和允许使用的表现层；
7. 玩家按钮能安全调用注册函数，但不能绕过模组权威状态；
8. 实时更新不造成全页闪烁、控件重建或风格不一致的等待页；
9. 普通终端不强制弹出，关键状态变化由后续 HUD/动态文本能力承载；
10. 所有页面达到 2B～2D 管理侧现有质量基线，并完成不同缩放、小窗口、多人、掉线、重连和请求重放验证。

[`MILESTONE-3A-TESTING.md`](MILESTONE-3A-TESTING.md)。自动检查通过不等于 V3A 完成；只有用户完成多人实机验收并明确收口后，才能更新为已完成。
