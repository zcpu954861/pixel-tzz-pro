## 2. 验收边界与安全

### 2.1 只使用可丢弃的新世界

不要在正式游玩世界、唯一存档或仍需保留的 2C 验收世界中测试。Schema v3 会保留活动游戏实例、时间线、预约、回调账本与回顾事实，旧测试数据会直接改变本轮可执行操作。

2026-07-29 已确认旧 `2D V1` 存档来自早期单字符串 NBT 保存实现：其冻结时间线
`normalized_json` 已为空，但 SHA-256 仍存在，因此会被当前版本正确识别为冻结文档损坏。当前代码已改为
`normalized_json_chunks` 分块持久化并有往返自检；旧世界不做猜测性修复，也不再承担后续验收。

推荐为本轮创建新的独立服务端世界目录，例如：

```text
run/server/world-2d-acceptance
```

若使用 `runServer`，必须先正常停服，并在 `run/server/server.properties` 中明确设置：

```properties
level-name=world-2d-acceptance
```

`level-name` 只写目录名，不写 `run/server/` 前缀。若 `server.properties` 尚不存在，先启动一次
`runServer` 生成服务端文件，正常停服后再修改。随后启动并让服务端生成新世界，再次正常停服，
把仓库示例数据包的完整副本放入：

```text
<新世界>\datapacks\Pixel-Tzz-Base-0.1.0
```

源目录：

```text
E:\minecraftserver\fabricmod\pixel-tzz-pro\examples\pixel-tzz-base-datapack
```

不要只覆盖少数 JSON 或函数。文件与定义的精确数量以本轮 `foundationSelfCheck`
断言、输出及示例 README 为准，不手工沿用 2C 数字。

| 顺序 | 任务 | 策略 | 时长 | 正式游戏计时 |
|---:|---|---|---:|---|
| 1 | `pixel_tzz:acceptance/warmup` | `event_only` | 无自动超时 | 否 |

分支任务结果：

| 结果 | 路线 | 间隔 |
|---|---|---:|
| `success` | 进入 `timeout_only` | `1200 Tick（60 秒）` |
| `failure` | 进入结束阶段 | `1200 Tick（60 秒）` |
| `timeout` | 进入结束阶段 | `1200 Tick（60 秒）` |

`timeout_only` 的 `finished` 结果进入结束阶段，最终间隔同样为 `1200 Tick（60 秒）`。四个示例间隔统一留出完整人工审阅和二次确认时间；它们仍属于各自冻结结果，而不是共享一个运行时计时器。
