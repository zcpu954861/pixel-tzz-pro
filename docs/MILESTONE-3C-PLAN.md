# V3C：数据驱动 HUD 与正式开局倒计时实施计划

状态：**产品语义、视觉方向、数据包契约、实施顺序与验收计划已冻结；代码实现与自动验证已完成，等待五客户端实机验收**

适用基线：

- Minecraft：`26.2`
- 当前模组版本：`0.1.0`
- 当前游戏 API：`api_version: 4`
- 当前网络协议：v13
- 当前世界状态：Schema v5
- 文档冻结日期：2026-08-04

## 0. 文档职责

本文固定 Pixel TZZ Pro V3C 的产品边界、视觉方向、权威模型、状态迁移、实施顺序和完成门槛。
精确资源路径、JSON 字段、默认值、引用约束与示例见
[`DATA-PACK-HUD-COUNTDOWN-API-3C.md`](DATA-PACK-HUD-COUNTDOWN-API-3C.md)，逐项五客户端验收入口见
[`MILESTONE-3C-TESTING.md`](MILESTONE-3C-TESTING.md)。

本文不是实机通过清单。文档中的 v13、Schema v5 与 API v4 已完成代码、迁移和自动验证；只有
五客户端实机验收完成后才能把 V3C 标记为最终通过。任何影响数据包作者或玩家设置的字段变更，
仍应先同步 API 与测试文档。

V3A 的玩家终端、可信字段和最小投影，V3B 的动态文本与声音，2D 的单任务时间线、双 Tick
时钟、冻结定义和回调账本均为 V3C 基础。V3C 不复制这些能力的第二套实现。

## 1. 阶段目标

V3C 解决两件彼此相关但边界清楚的事：

1. 在正常游戏中提供一个长期可见、低干扰、数据驱动的玩家信息位置；
2. 在主持人批准开局后，以服务端权威倒计时衔接赛前热身与正式游戏。

最终体验应做到：

- 玩家不打开终端也能检查数据包决定公开的当前信息；
- HUD 不占据多个屏幕角落，不与原版和其他模组争抢空间；
- 数据包能独立注册组件、字段、受众、路由、降级和玩家调整权限；
- 后台同步安静，不闪烁、不周期重播动画、不因 Tick 更新重绘全部组件；
- 主持人批准、倒计时、热身、全局计时和首个正式任务具有唯一权威时序；
- 掉线、Reload、重启、取消和回调失败不会造成重复开局或跳秒。

## 2. 明确不做的内容

V3C 不包含：

- 多个可自由漂浮的 HUD 小窗；
- HUD 内按钮、输入框、滚动正文或点击式游戏控制；
- 数据包任意脚本在客户端执行；
- 通用镜头锁定、路径、关键帧和电影黑边；这些属于 V3D；
- 致死拦截、捕获、旁观、存活权威状态机和复活；这些属于 V3E；
- 把 V3B 的临时提醒重新实现成 HUD；
- 把 2D 主持人 BossBar 直接删除或接管其他模组 HUD；
- 多 Game Profile 选择、并行任务或多局历史库；
- 在 HUD 中泄露主持人、OP 或数据包内部机器字段。

## 3. 核心产品原则

### 3.1 一个玩家只有一个常驻信息位置

每名玩家同一时刻最多显示一个持久 HUD 根布局，称为“信息坞”。根布局内部可以包含多个组件，
但组件不能各自移动到屏幕其他位置。数据包可以提供不同任务、身份和阶段的布局，路由器最终只
选择一个根布局，不把多个候选自动拼接。

正式开局倒计时是唯一临时中央覆盖层。它出现时不创建第二个常驻信息坞；普通提醒继续由 V3B
的 Chat、Title、Subtitle、ActionBar 和声音系统承担。

### 3.2 模组提供能力，数据包决定内容

模组提供：

- 严格资源解析、引用闭包和错误隔离；
- 服务端权威数据源、受众求交和最小投影；
- 一组有界且安全的 HUD 组件；
- 单根路由、布局测量、冲突避让和降级；
- 客户端插值、动画、音量、辅助功能与本地设置；
- 倒计时状态机、限制、恢复与回调账本。

数据包决定：

- 是否启用 HUD 与正式开局倒计时；
- 每一个组件显示什么、给谁看、何时出现；
- 根布局、路由、优先级、缺失值和降级策略；
- 玩家是否可以隐藏、紧凑、重排、移动、缩放或调节透明度；
- 倒计时时长、公开文案、声音、掉线策略、限制和生命周期回调。

### 3.3 显示不等于授权

客户端位置、透明度和动画属于表现偏好，不能决定玩家是否有权看到数据。服务端先对根布局、
组件、字段与实时上下文求受众交集，再构造该玩家独有的最终投影。未授权值从不下发；权限撤销
时敏感值立即清除。

## 4. 视觉方向

### 4.1 设计主题、单一任务与识别特征

- **设计主题**：持续存在的“全员逃走中”游戏信息坞；
- **单一任务**：玩家无需打开终端，就能迅速确认当前公开状态，同时不被界面抢走注意力；
- **识别特征**：稳定的底部“赛程脊线”，组件从脊线上方向上生长，阶段或进度在脊线上形成
  清晰标记。

默认验收原型锚定右下角安全区域。右下角更符合持续状态信息的阅读习惯，也不会与左侧聊天、
中央准星和下方热键栏形成同一视觉中心。它不是固定屏幕像素：安全区求解器会避让热键栏、
ActionBar、声音字幕和已登记的其他模组排除区域；玩家可在数据包许可范围内移动整个信息坞。

### 4.2 继承的视觉令牌

V3C 复用 3A/管理控制台的真实语义色，不另造一套主题：

| 令牌 | 颜色 | 用途 |
|---|---|---|
| `void` | `#09111A` | 半透明深底与高对比阴影 |
| `panel` | `#1A232E` | 信息坞主体 |
| `surface` | `#222E3A` | 局部抬升区与紧凑状态 |
| `border` | `#40505F` | 结构边界与非强调分隔 |
| `gold` | `#F2C14E` | 品牌、关键节点与倒计时完成 |
| `cyan` | `#55D7E6` | 当前进度、同步与信息强调 |

正文继续使用 `#F1F5F7`，次级正文使用 `#AAB4BE`；成功、警告、危险复用现有
`#5FD18A`、`#F2B84B`、`#D94B5B`，只在对应语义出现，不作为装饰色。

### 4.3 正常信息坞线框

以下线框只固定层级和形状，不固定数据包文案：

```text
屏幕右下安全区
                         ┌ 任务标记 ─────── 08:42 ┐
                         │ 寻找并启动「备用电源」 │
                         │ 进度  ███████░░  7 / 9 │
                         │ 存活  12   身份  逃走者 │
                         ├───────●───────────────┤
                         └ 赛程脊线 · 当前阶段 ──┘
```

脊线是整个信息坞唯一持续的高识别边界。正文区尽量使用留白、对齐和细分隔，而不是给每个字段
再套一张完整卡片。计时、进度与状态只有数据包注册且玩家获准时才存在。

### 4.4 紧凑信息坞线框

```text
                         ┌ 备用电源  7/9  08:42 ┐
                         └──────● 赛程脊线 ────┘
```

紧凑态保留任务识别、一个主要数值和时钟；不是把正常态整体缩成看不清的小字。哪些组件可被
摘要或隐藏由数据包声明，critical 内容不能因玩家偏好消失。

### 4.5 倒计时线框

```text
                              ┌──────────────┐
                              │  开局倒计时  │
                              │      05      │
                              │ ━━━━━●━━━━━ │
                              │  准备进入热身 │
                              └──────────────┘
```

倒计时位于中央安全区，但宽高有上限，不铺满屏幕、不遮住全部视野。简化动态模式只保留数字、
状态变化和必要声音；静态模式不做位移、缩放脉冲或闪烁。

### 4.6 通用化风险自检

首版最容易退化为“右下角三张卡片叠起来”：这会复制管理页的信息卡语言，造成边框过多、结构
碎片化、任何数据包看起来都一样。实现时必须坚持：

- 一个整体轮廓，而不是多个等权卡片；
- 脊线承担阶段与进度识别，不再额外增加标题框；
- 主要任务只保留一个视觉焦点；
- 次要字段通过列、分隔和字重组织，不滥用彩色矩形；
- 空组件完全收起，不为“看起来丰富”硬编码本局数据、身份或计时；
- 倒计时与常驻坞使用同一色彩语言，但轮廓、节奏和位置明显不同。

## 5. HUD 资源模型

V3C 使用四类独立资源：

1. `hud_components`：文本、进度、计时、容器等可复用组件；
2. `hud_layouts`：一个信息坞或倒计时覆盖层的根布局；
3. `hud_profiles`：Game 级路由、默认布局和客户端调整权限；
4. `countdowns`：服务端权威倒计时、限制、表现与回调。

Game 使用可选 `hud_profile` 和可选 `opening_countdown` 引用这些资源。旧 `api_version: 3`
Game 不引用 V3C 资源时继续保持现有行为；使用 V3C 字段的 Game 必须声明目标
`api_version: 4`。

组件通过稳定资源 ID 独立注册。根布局只引用组件 ID；容器也引用子组件 ID。引用图必须无环、
深度有界。高优先级数据包对同 ID 完整覆盖，不做字段级深合并，也不自动继承低优先级布局。

## 6. 单根路由

路由按以下层级选择：

1. 活动倒计时的中央覆盖层；
2. 当前任务命中的 task 路由；
3. 当前阶段、身份、队伍或状态命中的 context 路由；
4. HUD Profile 的 `default_layout`；
5. 无 HUD。

同一层中只比较显式整数 `priority`。最高优先级唯一候选获胜；同一最高优先级有两个候选同时
命中时，Profile 编译失败并保留上一代有效快照，不能按 JSON 顺序、资源 ID 或客户端本地偏好
猜测。不同根布局之间不自动合并、继承或叠加。

根布局内部可以根据组件受众自然收缩。所有组件消失时，根布局也必须消失，不绘制空框。

## 7. 组件与布局能力

首版支持：

- 文本与本地化富文本；
- 数据包资产图像与图标；
- 当前获准玩家的真实头像；
- 计数器与状态徽标；
- 水平或竖直进度条；
- 正计时、倒计时与静态时长；
- 背景、边框和分隔线；
- Row、Column 与 Overlay；
- 有界重复列表，以及超过上限后的摘要组件。

首版禁止：

- 任意像素脚本、着色器程序和客户端函数；
- 无限列表、滚动区域和任意深度递归；
- 输入、点击、拖动物品或游戏操作；
- 未登记字体、外部 URL 与运行时文件读取；
- 组件突破根布局到屏幕任意位置。

每个组件具有独立 ID、数据绑定、受众、优先级、样式和客户端调整权限。`critical`、`primary`、
`secondary`、`decorative` 四级只影响空间降级，不能提升数据权限。

## 8. 数据绑定与缺失值

HUD 复用 V3B 的类型与可信来源模型，允许读取：

- 游戏、阶段和当前任务事实；
- 当前玩家的身份、队伍、生存状态和已授权 Player Data；
- 已公开事件、统计、进度与结果；
- 游戏、任务、间隔、热身与倒计时时钟；
- 编译器批准的 Score、Storage 与受限实体/Data 来源。

Player Data 必须在自身 `surfaces` 中显式允许 `hud`。Score、Storage、Selector 和实体数据由
服务端解析；客户端只收到类型化结果，不收到可继续查询的路径、Selector 或隐藏对象。

缺失字段必须显式选择：

- 隐藏字段；
- 隐藏组件；
- 显示数据包注册的占位；
- 切换到注册的降级布局；
- 在有限 TTL 内保留非敏感旧值并显示 stale 标记。

当前关键值、倒计时状态、权限相关值和敏感值不能使用 stale。权限撤销不是“字段缺失”，必须
立即清除对应投影，不能显示旧值或占位暗示其存在。

## 9. 原子快照与静默刷新

服务端把一次 HUD 投影视为不可分割快照，至少带有：

- 游戏实例与冻结 definition generation；
- HUD epoch、context version 和 snapshot sequence；
- 获胜根布局与已授权组件树；
- 服务端 Tick 锚点和可插值时钟；
- 当前玩家获准的最终值与客户端调整权限。

结构变化使用原子替换，数值更新使用带版本的有界补丁；客户端只在完整校验后于同一帧提交，
不能出现旧任务标题配新任务进度。过期、乱序、重复或跨 epoch 补丁直接丢弃。

普通 Tick、心跳和相同值刷新不触发：

- 根布局重新创建；
- 进入动画；
- 全组件透明度闪烁；
- 右上角同步徽标；
- 声音。

计时器根据服务端 Tick 锚点在本地插值。服务端周期校正只调整内部锚点；误差未超过阈值时平滑
收敛，超过阈值时原子校正数值但不重播进入动画。

## 10. 安全区、响应式与降级

默认参考画布沿用现有 `640×360` 逻辑尺寸与 `2560×1440 + GUI Scale 4` 的已验收比例。
更小窗口把信息坞、文字、线宽、裁剪和命中区域一起等比缩放；更大窗口设置最大视觉尺寸，
不无限放大。

安全区求解器至少考虑：

- 屏幕边缘与玩家配置的安全边距；
- 热键栏、经验条、ActionBar、BossBar、聊天和声音字幕；
- 当前 GUI Scale、字幕设置与可见原版 HUD；
- 客户端配置或兼容桥登记的其他模组排除矩形；
- 当前数据包允许的锚点与移动范围。

空间不足时按固定顺序处理：

1. 使用组件注册的 compact 形式；
2. 在同一个信息坞内使用替代排列；
3. 收紧允许收紧的间距；
4. 使用注册的摘要组件；
5. 隐藏允许隐藏的低优先级内容；
6. 拒绝当前布局并使用注册的 degradation layout；
7. 降级布局仍失败则清空 HUD 并给主持人诊断，普通玩家不显示红字。

不得通过无限缩小、文字越界、负间距、裁切 critical 内容或增加滚动条掩盖失败。

## 11. 屏幕可见性与其他 HUD

信息坞：

- 正常游戏中可见；
- 打开聊天输入框时继续可见，但避让展开后的聊天区域；
- F1 隐藏；
- 库存、容器、设置、终端、主持人控制台、数据页和强制流程页显示时隐藏；
- 普通暂停菜单及未登记 Screen 默认隐藏；
- TAB 发生碰撞时按本地策略临时调暗或隐藏；
- Screen 关闭后原位恢复，不重播进入动画。

V3C 不修改其他模组的 HUD。冲突通过自身安全区、排除矩形、紧凑和降级处理。若第三方模组
没有提供位置 API，玩家可以在“避让区域”页面登记矩形；诊断页只显示几何与来源，不读取或
控制第三方模组内容。

## 12. 本地设置与权限

设置入口固定为：

```text
选项
└─ 全员逃走中设置
   └─ HUD 与倒计时
```

“全员逃走中设置”继续使用一行两列分类目录。HUD 与倒计时下分为：

1. 全局 HUD 显示；
2. 布局编辑；
3. 组件管理；
4. 避让区域；
5. 倒计时表现；
6. 重置与诊断。

所有编辑采用草稿、应用、取消。离开页面或按 ESC 时，未应用草稿必须二次确认丢弃或继续编辑，
不能边拖动边永久写配置。组件管理列表只在自身区域滚动；预览和底部操作始终可达。

数据包可以分别声明：

- 是否允许完全隐藏 HUD；
- 允许的锚点和偏移范围；
- 缩放与透明度范围；
- 哪些组件可隐藏、紧凑或重排；
- HUD 与倒计时的默认音效和视觉表现。

玩家偏好永远不能：

- 扩大受众或解锁组件；
- 延迟、暂停、跳过或快进权威倒计时；
- 把组件移出安全范围；
- 隐藏数据包锁定为 critical 且 `allow_hide: false` 的信息；
- 强制其他玩家使用相同位置或表现。

玩家始终可以分别静音 HUD 与倒计时，也始终可以把动态强度降到 `simplified` 或 `static`；
数据包不能声明最低本地音量或禁止动态降级。

辅助功能提供高对比、HUD 音量、倒计时音量和三档动态强度：

- `full`：完整但受全局安全上限约束；
- `simplified`：移除无必要脉冲、位移和逐段进入；
- `static`：只保留最终状态变化，不闪烁、不缩放、不滑入。

数据包不能强制闪烁、剧烈运动、不可读透明度或高音量。数据包锁定显示不等于可以突破客户端
安全下限。

## 13. 倒计时权威时序

Game 可以不注册倒计时。没有 `opening_countdown` 时，主持人批准继续使用现有 2D 原子立即
开局行为。存在倒计时时，时序固定为：

1. 玩家完成初始化与准备；
2. 主持人审阅并批准；
3. 服务端原子冻结参与者、可达任务计划、HUD/倒计时定义和回调；
4. 进入 `COUNTDOWN`，运行正式开局倒计时；
5. 倒计时完成；
6. 进入数据包注册的热身游戏；
7. 热身结束；
8. 全局游戏时钟与第一个正式任务同时开始。

倒计时和所有 `kind: warmup`、`counts_toward_game_time: false` 的赛前环节不计入全局游戏
时长。热身可以使用自己的任务时钟。若首个任务就是正式任务，倒计时完成时直接启动全局时钟
与该任务。

数据包引用倒计时并声明 `required: true` 时，缺失、解析失败、引用闭包无效或必需资产不可用
都会阻止主持人批准。`required: false` 才允许在明确诊断后降级为无倒计时立即开局。

## 14. 倒计时状态与控制

权威状态至少区分：

- `running`：正常扣减；
- `waiting_for_players`：所需参与者缺失，剩余 Tick 冻结；
- `recovery_wait`：服务器恢复后等待连接协调，剩余 Tick 冻结；
- `completing`：完成回调与首个环节原子提交中；
- `canceling`：取消回调与回退提交中。

主持人不能跳过或快进。取消入口只在阶段感知主持人控制台出现，使用现有高风险二次确认框架，
令牌必须绑定游戏实例、倒计时实例、状态版本、目标操作和到期 Tick。服务器状态变化后旧确认
失效，重新审阅必须打开当前权威确认，不得弹两层错误。

取消成功后：

- 回到 Game 注册的等待批准阶段；
- 保留玩家身份、初始化结果、准备和开局前字段；
- 丢弃本次冻结的倒计时/任务候选；
- 记录原因与已成功回调；
- 不自动开始下一次倒计时。

## 15. 掉线、Reload 与恢复

所需参与者掉线策略：

- `pause`：默认；暂停并等待同一冻结 UUID 返回，条件恢复后从原剩余 Tick 继续；
- `cancel`：执行权威取消并回到等待批准；
- `continue`：缺失玩家不阻止倒计时，但不会因此扩大受众或修改冻结参与者。

主持人掉线策略独立配置，默认 `continue`。主持人掉线不会把 OP 自动提升为主持人，也不会把
控制台权限发给普通玩家。

`/reload`：

- 继续使用倒计时启动时冻结的 definition generation；
- 不用新资源中途替换布局、声音、限制或回调；
- Reload 执行时间不额外扣除或补偿 Tick；
- 新 generation 只影响下一次主持人批准。

正常服务器关闭与重启：

- 持久化实例 ID、状态版本、剩余 Tick、冻结定义、参与者、限制恢复信息和回调账本；
- 启动后先进入 `recovery_wait`；
- 客户端尚未完成必要连接协调时不倒数；
- 恢复同一实例，不重播已成功 start 回调、声音或完整进入动画；
- 冻结快照损坏时 fail closed，不立即开局，由主持人获得诊断和安全取消入口。

## 16. 倒计时限制

默认参与者限制为：

- 冻结位置移动与速度推进；
- 阻止攻击；
- 阻止方块、实体和物品交互；
- 阻止丢弃、交换和使用物品；
- 提供临时伤害免疫。

镜头转动、第三人称切换、聊天与 ESC 继续可用。V3C 不锁定或动画化摄像机。

限制通过事件门和独立权威状态实现，不通过永久药水效果、改游戏模式或覆盖玩家无关属性模拟。
进入倒计时前只保存恢复所需的最小状态；完成、取消、重启恢复、退出参与者和错误回退都必须
幂等解除。重复解除不能把其他模组之后添加的状态恢复成旧值。

## 17. 倒计时表现与回调

倒计时定义引用 `surface: countdown` 的 HUD Layout，获得只读 `countdown.*` 字段。中央覆盖层
可以使用文本、图像、进度、计时和容器组件，但不能读取比普通信息坞更多的数据。

视觉动画以服务端剩余 Tick 为事实源。客户端低 FPS、切屏或声音缺失不延迟完成；客户端也不能
上报“动画完成”推动服务端。

生命周期回调包括 start、pause、resume、cancel、complete。回调：

- 只在服务端执行注册 `mcfunction`；
- 以倒计时实例、回调槽、发生序号和可选逐玩家键记账；
- 成功项至多一次，失败项可由主持人按原上下文重试；
- `complete` 全部必需项成功后才启动热身或正式任务；
- 客户端预览、设置、HUD 显示和诊断永不执行回调；
- 回调失败不会把倒计时重新放回 `running` 或重复最后一秒。

## 18. 预览与诊断

普通玩家预览只使用当前已经授权的真实组件与脱敏值。预览不能显示未来任务、其他身份专属数据
或数据包路径。

主持人开发预览位于现有管理/预览体系，可模拟：

- 身份、队伍、阶段、任务与生存状态；
- 常规、紧凑、摘要与最小布局；
- 不同分辨率、GUI Scale 和安全区；
- 长中文、长玩家名、Emoji、缺失值和 stale；
- 重复列表上限与溢出摘要；
- 倒计时起点、关键秒、暂停、恢复和完成前一 Tick。

预览只在本机创建隔离渲染快照，不写世界状态、不发其他客户端、不执行回调、不建立历史、不
创建正式倒计时。诊断继续提供“简洁汉化 / 原始详情”切换；普通玩家永远不接收资源路径、
NBT 路径、Selector、异常栈或机器注册键。

## 19. 性能与硬边界

实现必须对下列项目设置编译期或运行时硬上限，并在 API 文档中与代码保持一致：

- 每代 HUD Profile、Layout 和 Component 数量；
- 单根引用深度、展开节点数、Row/Column 子项和 Overlay 层数；
- 重复列表项目数与溢出摘要；
- 文本字素、行数、图像尺寸、进度与计时范围；
- 每玩家快照字节数、补丁频率、待处理版本和诊断数量；
- 排除矩形数量、客户端草稿数量和本地配置大小；
- 活动倒计时、检查点、声音、回调与恢复记录数量。

精确数值在实现阶段通过 32/64 人模拟、长文本和低 FPS 压力确定，不在计划阶段凭感觉写死。
任何软限制都不能超过模组硬限制。超限资源隔离；已有有效 generation 继续工作。

## 20. 实施架构

V3C 应沿现有模块边界增加能力，而不是把 HUD、网络、状态和 UI 全塞入一个类：

- content：资源 records、严格 parser、引用闭包和编译目录；
- server：HUD 路由、受众投影、快照/补丁、倒计时权威和限制门；
- state：Schema v5 倒计时实例、冻结快照、回调账本与迁移；
- network：v13 payload、大小限制、序列与重同步；
- client HUD：快照缓存、布局测量、安全区、渲染、插值和屏幕可见性；
- client settings：本地偏好、草稿、布局编辑、排除区域和诊断；
- integration：2D 审批/时间线、V3A 字段、V3B 声音/提醒、TAB 与原版 Screen。

服务端纯逻辑权威必须可在没有 Minecraft 客户端的 SelfCheck 中测试。客户端布局测量与命中必须
使用统一参考画布；不能让渲染缩放与点击、拖动、排除区域坐标使用不同坐标系。

## 21. 实施顺序

### 21.1 3C-1：资源与编译

- 实现 API v4、四类资源、严格 parser、覆盖与引用闭包；
- 编译单根路由、组件 DAG、受众闭包、降级闭包与错误隔离；
- 添加示例数据包与有效/无效夹具。

### 21.2 3C-2：HUD 权威与协议

- 实现服务器路由、数据绑定、最小投影和原子快照；
- 升级 v13 payload、顺序、补丁、clear 与重同步；
- 验证撤权、非主持人 OP、乱序、重复与大小边界。

### 21.3 3C-3：客户端信息坞

- 实现右下角默认坞、赛程脊线、组件测量与渲染；
- 实现安全区、排除区域、紧凑/摘要/降级和屏幕可见性；
- 实现本地计时插值、静默更新和三档动态强度。

### 21.4 3C-4：设置与预览

- 在两列设置目录中加入“HUD 与倒计时”；
- 完成六个子页、草稿/应用/取消、锁定原因和布局编辑；
- 完成普通玩家授权预览、主持人开发预览和双模式诊断。

### 21.5 3C-5：正式倒计时

- 拆分 2D 批准与首任务启动；
- 实现 Schema v5 状态、限制、掉线策略、取消确认和回调账本；
- 实现 Reload 冻结、重启 recovery wait、热身与全局时钟衔接。

### 21.6 3C-6：收口

- 补齐 32/64 人、低 FPS、长文本、不同 GUI Scale 和第三方 HUD 避让；
- 执行完整自动门；
- 按验收手册逐项完成五客户端测试和集中修复；
- 用户明确确认后再提交、推送和合并。

## 22. 自动与实机验证

自动检查必须覆盖资源、路由、受众、快照、协议、持久化、迁移、倒计时状态、限制、回调账本、
设置序列化和旧版本兼容。目标任务名与分组见验收手册；实现时应接入 `check.dependsOn`。

自动检查不能证明：

- 右下角是否真正避开热键栏、ActionBar 与声音字幕；
- 中文、Emoji、头像和长文本是否视觉正确；
- 刷新是否闪烁；
- 五端倒计时声音和动画是否一致；
- 玩家是否觉得信息占用过多；
- 不同窗口、GUI Scale、F1、TAB、聊天与第三方 HUD 是否自然。

这些项目必须由用户在真实 Minecraft 多客户端中逐项确认。实施阶段遇到视觉反馈，应按一轮
完整记录、集中修复、定向回归的节奏进行，不在测试中途把每个截图立即改成互相冲突的补丁。

## 23. V3C 完成定义

V3C 只有同时满足以下条件才算完成：

1. HUD 组件、布局、Profile 与倒计时完全由严格数据包资源注册；
2. 每名玩家同一时刻只有一个持久信息坞，倒计时是唯一中央例外；
3. 路由唯一、无隐式继承，同优先级冲突能阻断错误 generation；
4. 根、组件、字段和上下文受众闭包正确，隐藏数据从不下发；
5. 右下角默认布局、赛程脊线、安全区和响应式降级达到 V3 质量基线；
6. 刷新、补丁、计时插值和 Screen 恢复不闪烁、不重建、不重播；
7. 本地设置受数据包权限约束，并具备草稿、应用、取消、重置和诊断；
8. 完整、简化、静态、高对比和独立音量均可用且不改变权威时钟；
9. 无倒计时数据包保持 2D 立即开局兼容；
10. 有倒计时时严格执行批准、倒计时、热身、正式计时顺序；
11. 掉线、取消、Reload、重启和回调失败不会跳秒、重复开局或重复成功回调；
12. 倒计时限制完整且幂等恢复，不改变游戏模式、永久效果或无关属性；
13. 示例数据包、API 文档、诊断与测试命令一致；
14. 完整自动检查、独服回归和用户逐项五客户端实机验收全部通过；
15. 用户明确确认 V3C 收口。

在这些条件满足前，V3C 只能标记为“文档已冻结”或“实现/验收中”，不能宣称已完成，也不能
提前把 V3D 镜头或 V3E 捕获能力混入本阶段。
