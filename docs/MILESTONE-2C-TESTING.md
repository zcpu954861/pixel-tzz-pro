## 2. 测试边界与安全要求

### 2.1 只使用可丢弃测试世界

不要直接使用未来正式游玩世界，也不要在唯一存档上制造回调或资源故障。

推荐新建一个专用开发世界；若必须复制旧世界，先完整备份整个世界目录。2C 当前没有把“删除世界状态文件”作为日常重置流程，因此不要为了清进度手工删除：

```text
<测试世界>\data\pixel-tzz-pro\world_state.dat
```

需要从零复验时，新建世界或恢复整个测试世界备份。

### 2.2 玩家准备

核心链路至少需要两个不同 UUID 的真实玩家：

| 玩家 | 权限 | 用途 |
| --- | --- | --- |
| 玩家 A | OP 等级至少 2 | 认领主持人并操作控制台 |
| 玩家 B | 普通玩家 | 逃走者、强制流程成员和身份调整目标 |

成功补充新成员还需要玩家 C，或一个能提供第三个不同 UUID 的临时测试客户端。只有 A、B 两人时仍可测试移除和取消，但不能把“补充成员成功”标为通过。

32/64 人 UI 压力页可以使用开发预览器的模拟上下文；若没有 32/64 个真实连接，不得把模拟页面结果写成“32/64 个真实在线玩家服务端压力已通过”。

### 2.3 客户端和服务端

推荐使用独立的可丢弃开发服务端，玩家 A、B 使用两个客户端连接。两端必须安装同一份本轮构建的 `Pixel-Tzz-Pro-0.1.0.jar`，并保持 Minecraft、Fabric Loader 和 Fabric API 版本一致。

基础数据包源目录：

```text
E:\minecraftserver\fabricmod\pixel-tzz-pro\examples\pixel-tzz-base-datapack
```

将其复制到测试世界，例如：

```text
<测试世界>\datapacks\Pixel-Tzz-Base-0.1.0
```

不要假设 `run/client` 或 `run/server` 中已有的数据包副本仍与仓库一致。复验前必须完整替换为上面 38 文件的仓库示例；不要只启动既有开发世界后直接测试，否则可能看不到 2C 的四个执行页面和最新回调。

基础资源包源目录：

```text
E:\minecraftserver\fabricmod\pixel-tzz-pro\examples\pixel-tzz-base-resourcepack
```

将其安装并在两个客户端启用。正常链路测试时不要启用：

```text
E:\minecraftserver\fabricmod\pixel-tzz-pro\examples\pixel-tzz-required-asset-fixture
```

每个客户端首次进入后，确认模组握手成功；缺少客户端模组、协议不一致或握手超时时停止测试并保存日志。

### 2.4 留证

每个失败项至少记录：

- 当前测试小节和操作顺序；
- 玩家 A、B、C 的身份和在线状态；
- 活动流程短 ID、完成数/总数和当前节点；

- 客户端 `latest.log` 和服务端日志中的稳定拒绝码；

不要连续点击制造刷屏。一次操作、一次观察、一次记录即可。

## 4. 新世界、握手与主持人认领

1. 启动专用开发服务端，等待服务端明确进入 `Done`。
2. 玩家 B 先进入，打开 ESC 中的“全员逃走中”入口。
3. 确认 B 看到玩家侧页面，不能看到可提交的主持人高风险操作。
4. 玩家 A 进入；确认 A 为 OP 等级至少 2。
5. A 打开 ESC 中的“全员逃走中”入口。
6. 确认首页优先提示“尚未指定主持人”，并提供“认领主持人”。
7. 点击认领；第一次点击只能进入二次确认，不能立即写入。
8. 检查确认页写明当前世界、操作者、权限后果、不可由普通玩家代替等信息。
9. 最终确认。
10. 重新打开 ESC；入口和页面应切换为管理员控制台，主持人显示 A。
11. B 再次打开入口；仍不得获得管理员控制权。

通过条件：

- 认领只成功一次；
- A 的 ESC 入口按服务器状态切换为管理员面板；
- B 不能伪造认领或主持人操作；
- 操作前后的 UI 都没有提前修改阶段、身份或流程。

## 5. 通用初始化：`if_incomplete`

验收对象：

```text
操作：pixel_tzz:start_general_initialization
流程：pixel_tzz:general_tutorial
策略：if_incomplete
页面：fixture/general/briefing → fixture/general/confirm → complete
```

1. 保持 A 为主持人、B 在线且为默认逃走者。
2. A 打开管理员控制台；首页应把当前阶段最可能需要的操作放在首要区域。
3. 打开“全部操作”，选择“发起通用初始化”。
4. 此操作不手工选人；由服务端按当前 audience 锁定在线且合格的参与者。
5. 阅读二次确认，确认其中明确写出：名单会锁定、页面不可关闭、完成后不自动准备或开局。
6. 最终确认一次。
7. B 应立即进入“2C 通用初始化验收”说明页；A 作为主持人不应被计入参与者。
8. 在 B 上按 Esc，并尝试用普通页面入口替换当前界面。
9. 强制页面应继续占据前台；它不能被当成完成，也不能靠 Esc 自行解除。
10. A 应看到仅主持人可见的 BossBar，名称类似“通用初始化: 0/1”。
11. B 点击“我已阅读，继续确认”，进入最终确认页。
12. B 明确确认后，服务端提交完成，页面立即解除。
13. A 的 BossBar 应变为 `1/1`，播放一次完成反馈后按配置消失。
14. 检查阶段没有自动推进，游戏没有自动开始。
15. A 再次发起同一操作。

第二次发起的通过条件：

- B 的同一流程版本完成记录被识别；
- B 不再打开强制页面；
- 不创建总数为 0 的空活动实例；
- 操作返回“当前目标已经完成”一类明确结果，而不是静默卡住。

## 6. 猎人初始化：`always` 与身份延后提交

验收对象：

```text
操作：pixel_tzz:assign_hunter
流程：pixel_tzz:hunter_initialization
策略：always
身份提交：after_flow
```

1. A 从“全部操作”选择“指定或重新初始化猎人”。
2. 在服务端下发的玩家列表中选择 B。
3. 确认目标卡显示 B 当前真实身份和在线状态；选择数量为 `1`。
4. 进入二次确认，检查标题、目标、阶段、操作后果和 `always` 语义。
5. 最终确认。
6. B 进入猎人初始化说明页。
7. 在 B 完成前打开 TAB；B 仍应显示为原身份，不能提前出现猎人前缀或红色猎人样式。
8. B 进入最终确认页并完成。
9. 完成响应到达后再次查看 TAB 和管理员名单；B 才正式变为猎人。
10. A 再次对已经是猎人的 B 发起相同操作。
11. B 必须再次进入猎人初始化，证明 `always` 没有被历史完成记录跳过。
12. B 完成第二次流程；身份保持猎人，不产生重复成员完成或重复回调状态。

通过条件：

- 身份在自然完成前不变；
- 身份和完成记录在一次服务端提交后同时可见；
- 已是猎人的玩家仍按 `always` 重新执行；
- 双击或旧页面请求不能多提交一次身份。

## 7. 活动流程名单：补充、移除与取消

### 7.1 补充成员

此项需要 A、B、C 三个不同 UUID。

1. A 对 B 单独发起猎人初始化。
2. B 停留在说明页，不完成。
3. C 在线，并保持为符合该流程 audience 的玩家。
4. A 打开“当前强制流程”。
5. 检查当前为 `0/1`，未完成人员为 B。
6. 选择“补充成员”，选择 C，阅读二次确认并确认。
7. BossBar 分母应从 `1` 变为 `2`。
8. C 应从入口节点打开强制页面；B 的当前节点不得被重置。
9. 已在实例中的 B 不应再次出现在可补充目标中。

### 7.2 移除成员

1. 在上一实例中让 C 停留在说明页。
2. A 选择“移除成员”，选择 C，阅读后果并确认。
3. C 的强制页面应立即解除。
4. 分母从 `2` 回到 `1`；C 不得得到流程完成记录。
5. 若 C 有待猎人身份变更，该待变更应取消，C 的正式身份不变。
6. B 的节点和待身份变更保持原样。
7. B 正常完成；实例按剩余成员正常结束。

只有 A、B 两人时，可以对唯一成员 B 执行移除。此时应释放 B 页面并结束或取消无剩余成员的实例，但这不能代替“补充成员成功”测试。

### 7.3 取消整个实例

1. 再次对 B 发起猎人初始化，让 B 停在说明页。
2. A 从活动流程页选择“取消实例”。
3. 二次确认必须写明：所有未完成页面会解除、未完成待身份变更会取消、自然完成历史不会伪造。
4. 最终确认。
5. B 的页面立即解除；BossBar 清除。
6. B 的正式身份保持取消前状态。
7. 当前实例标记为取消，随后允许发起新的流程。

## 8. 离线与重连

1. A 对 B 发起猎人初始化。
2. B 从说明页进入最终确认页，但先不完成。
3. 记录活动实例短 ID、节点和 BossBar 分母。
4. B 正常退出服务器。
5. A 的 BossBar 分母不得减少；活动页应把 B 标为离线而不是完成。
6. B 重新连接。
7. 握手完成后，服务端应重新打开同一冻结节点。
8. 重连后的页面实例 ID 应是新会话；断线前的旧页面请求不能推进当前节点。
9. B 完成流程。

通过条件：

- 离线不打断活动实例、不伪造完成、不改变分母；
- 重连恢复的是服务端节点，不是客户端本地记忆；
- 恢复后只完成一次。

## 9. 正常停服与重启

此项必须使用专用服务端；不要用强制结束进程代替正常停服。

1. 发起一个新的猎人初始化，让 B 停在最终确认页。
2. 记录主持人、活动实例短 ID、节点、完成数/总数和 B 的正式身份。
3. 在服务端控制台执行正常 `stop`。
4. 等待世界保存和 Java 进程完整退出。
5. 重新启动同一服务端和同一世界。
6. A、B 重新连接并完成握手。
7. A 仍是主持人；活动实例、成员、节点和待身份变更仍在。
8. A 的 BossBar 恢复正确值。
9. B 恢复到停服前节点，完成后只提交一次身份和回调。

如果出现快照哈希或引用错误，应进入明确 `blocked` 诊断；不得偷偷改用最新数据包继续推进。

## 10. `/reload` 与冻结 execution snapshot

此项只修改测试世界里的数据包安装副本，不修改仓库 `examples` 源文件。先备份将要编辑的 JSON。

1. 对 B 发起 `always` 猎人初始化，让 B 停在 `fixture/hunter/briefing`。
2. 在安装副本中找到：

   ```text
   data\pixel_tzz\pixel_tzz_pro\pages\fixture\hunter\confirm.json
   ```

3. 备份该文件，并只改一段容易辨认、仍符合 Schema 的显示文案，例如追加“NEW GENERATION TEST”。
4. 从服务端控制台执行一次 `/reload`，避免为了输入命令关闭 B 的强制页面。
5. 等待 definition generation 成功更新。
6. B 应保持或重新打开同一强制页面，随后从说明页继续到确认页。
7. 当前活动实例必须仍显示创建实例时冻结的旧文案。
8. B 完成当前实例。
9. A 再次对 B 发起猎人初始化。
10. 新实例应显示新文案，证明它使用了 reload 后的新 generation。
11. 恢复备份文件，再执行一次 `/reload`。

全过程检查：

- 主持人没有被清除；
- B 的正式身份、完成历史和当前节点没有被 reload 清除；
- reload 会销毁尚未消费的二次确认令牌，但不销毁活动流程；
- 当前实例不被新页面、主题、predicate 或流程定义污染。

## 11. 二次确认：透明续期、双击和旧请求

三项测试都从一个当前可执行、尚未创建活动实例的操作开始。每次测试前确认没有遗留活动流程。

### 11.1 服务端令牌自然过期

1. A 打开任一高风险操作的二次确认页。
2. 不点击最终确认，等待至少 `31` 秒。
3. 再点击最终确认。
4. 客户端不得要求第二次点击，也不得重新绘制一个新的确认页；可在原按钮位置短暂显示“正在校验并执行”。
5. 若权限、阶段、目标和后果均未变化，客户端应自动取得新令牌并完成该操作一次。
6. 旧令牌本身必须先被服务端拒绝或消费；最终只允许新令牌对应的提交生效一次。
7. 若等待期间业务上下文已经变化，必须停止自动提交并要求人工重新审阅变化后的内容。

### 11.2 快速双击

1. 重新打开确认页获得新令牌。
2. 对最终确认按钮快速双击一次。
3. 最多一个请求成功；第二次应被按钮门控、单次消费或请求防重放拒绝。
4. 活动实例、身份变更和审计中的成功提交都只能出现一次。

### 11.3 旧令牌与旧上下文

1. 再打开一个确认页，并保持该页面不动。
2. 从服务端控制台执行 `/reload`；reload 会销毁内存确认令牌。
3. 回到仍显示旧确认上下文的客户端，点击最终确认。
4. 服务端必须以 `confirmation_missing`、`confirmation_context_changed` 或相应稳定代码拒绝。
5. 不得执行任何部分操作。

Vanilla UI 不提供任意网络包重放器。精确复发相同 request sequence 的覆盖由 `controlRequestGateSelfCheck` 和 `protocolV7SelfCheck` 承担；若没有抓包/注入工具，实机记录应写“旧确认上下文已测，原始网络包重放由自动自检覆盖”，不能伪写为人工抓包通过。

## 12. 回调失败、恢复与人工重试

示例回调本身只有注释，没有聊天输出，因此这项测试不会用 `tellraw` 刷屏。

只操作测试世界中的数据包安装副本。开始前备份：

```text
data\pixel_tzz\function\hunter\player_complete.mcfunction
```

推荐步骤：

1. A 对 B 发起猎人初始化。
2. B 停在最终确认页。
3. 将安装副本中的：

   ```text
   player_complete.mcfunction
   ```

   临时改名为：

   ```text
   player_complete.mcfunction.disabled
   ```

4. 从服务端控制台执行一次 `/reload`。
5. B 点击最终确认。
6. 核对核心状态已经按权威提交：B 不会退回旧节点，也不会因回调失败而重复完成。
7. A 的活动流程页应显示回调失败和明确诊断，实例进入阻塞而不是假装成功。
8. 将文件名恢复为 `player_complete.mcfunction`。
9. 再执行一次 `/reload`。
10. A 从活动流程诊断选择对应“重试回调”。
11. 重试仍必须进入二次确认，并清楚写明“只重试回调，不重新完成玩家、不重复修改身份”。
12. 最终确认一次。
13. 回调成功后阻塞诊断解除；B 不重新打开页面，完成历史和身份不增加第二份。

结束后核对安装副本已恢复，仓库 `examples` 源文件未被改动。若 reload 后定义候选本身被拒绝，先保存诊断并恢复文件；不要连续点击重试掩盖第一个错误。

## 13. 资源错误

### 13.1 可选资源回退

1. 保持只启用基础数据包和基础资源包。
2. A 打开“开发与诊断”中的页面预览器。
3. 打开 `pixel_tzz:hunter/acknowledge`。
4. 页面故意缺少：

   ```text
   pixel_tzz:textures/gui/optional_preview_art.png
   ```

5. 应显示原版警告图标 fallback；页面仍可浏览，不进入必需资源安全错误页。

### 13.2 必需资源缺失

1. 将以下夹具复制到测试世界 `datapacks`，不要覆盖基础数据包：

   ```text
   E:\minecraftserver\fabricmod\pixel-tzz-pro\examples\pixel-tzz-required-asset-fixture
   ```

2. 使用命令补全确认实际 pack ID，然后启用该数据包：

   ```mcfunction
   /datapack enable "file/pixel-tzz-required-asset-fixture"
   ```

   命令会触发资源重载；等待 reload 完成。

3. 从预览器打开：

   ```text
   pixel_tzz_fixture:required_asset_error
   ```

4. 客户端不得渲染残缺业务页，应显示模组内置安全错误页。
5. 错误页应给出缺失资产、必需性、重新检查资源、设置或安全断开等明确操作。
6. 服务端只接受当前页面实例内、数量有界且能与预期资源匹配的报告。
7. 测试后禁用该夹具，并确认基础 generation 恢复健康：

   ```mcfunction
   /datapack disable "file/pixel-tzz-required-asset-fixture"
   ```

资源错误不能把玩家标记为完成；若在强制上下文复验，应保持实例为可诊断阻塞状态。

## 14. 旁观者与恢复参与

此项放在其余猎人、名单、重启和回调测试之后，避免旁观者不再符合后续参与者筛选。

验收对象：

```text
操作：pixel_tzz:set_spectator
身份：pixel_tzz:spectator
提交：immediate
```

前提：当前没有活动强制流程。未完成任何初始化的玩家 C 也必须可以参加本项测试。

1. A 从“全部操作”打开“设为旁观者”。
2. 先确认名单中的 B/C 都显示初始化状态；未完成教程者应显示“未初始化”。
3. 选择未初始化的 C。主持人不得出现在名单中。
4. 检查二次确认明确写明：立即变为旁观者、不再参与准备和掉线提醒、历史完成记录保留。
5. 最终确认。
6. C 不应打开任何初始化流程页面。
7. 服务端确认后，管理员名单与 TAB 立即显示旁观者身份。

### 14.1 已初始化猎人或旁观者立即恢复

1. 将已经完成当前版本 `general_tutorial` 的 B 设为旁观者。
2. A 打开“恢复为逃走者”，名单只能出现符合条件的已初始化猎人或旁观者。
3. 确认后 B 立即恢复为逃走者，不打开强制流程页面。
4. B 的教程完成历史保持不变。

### 14.2 未初始化猎人或旁观者先初始化再恢复

1. C 保持未初始化旁观者身份。
2. A 打开“初始化并恢复为逃走者”，名单只能出现尚未完成当前版本教程的猎人或旁观者。
3. 确认后 C 进入数据包注册的通用初始化页面，完成前仍是旁观者。
4. C 完成后服务端原子提交逃走者身份；取消流程则继续保持旁观者。

通过条件：

- 这是一次有确认保护的原子身份提交；
- 不创建空流程或待身份事务；
- 活动流程存在时该操作应禁用或被权威拒绝。
- 两条恢复路径按当前版本初始化状态互斥，不会同时列出同一玩家。

## 15. BossBar、UI、强制关闭和声音

在以上各条主流程中同步检查：

### 15.1 BossBar

- 只有当前主持人看到 BossBar；
- 参与流程的普通玩家、猎人和旁观者不因“在线”自动看到；
- 标题为彩色的 `<事件名称>: <完成数>/<总数>`；
- 补员、移除、离线、重连和完成后数值正确；
- 离线只改变分类，不改变分母；
- 主持人仍停留在模组界面时，满格停留、完成音和渐隐倒计时暂停；
- 主持人明确回到 HUD 后，完成反馈只播放一次，再按 `hold_ticks` 和 `fade_ticks` 消失；
- 取消后立即清除，不残留旧实例进度。

### 15.2 UI 与交互

- 控制台首页随“无主持人 / 可执行操作 / 活动流程 / 阻塞诊断”改变主内容；
- 中文主标题醒目，英文辅助标签弱化，不抢主语言层级；
- Compact、Standard、Wide 三类宽度均不溢出屏幕；
- 目标选择列表可搜索、滚动，卡片边框不与容器重叠；
- 返回按钮箭头有悬停动画，但按钮命中区域和整体位置不移动；
- 其他按钮有清楚的颜色、描边或光带反馈，不退化为原版灰按钮；
- 点击后等待服务端响应时只改变当前事务按钮和右上角同步徽标，其余按钮不重建、不闪烁、不重播悬停动画；
- 前进、返回、替换、关闭的转场方向一致；
- 强制页面自然解除时没有黑帧、世界闪烁或短暂显示错误页面；
- 二次确认完整显示操作、目标、阶段、后果和可撤销性，不向玩家显示内部令牌剩余时间；
- 多人确认最多堆叠两个真实皮肤头像，超过两人时头像栈右下角显示省略号，并显示“首位玩家等 N 人”摘要；“查看全部受影响玩家”按钮不与卡片边框重叠，可进入完整名单并原样返回同一确认；
- 确认失效后主按钮改为非危险态“重新审阅”，底部按钮在所有 GUI scale 下均保持在面板完整外框内。

### 15.3 声音

- 鼠标仅悬停不播放声音；
- 一次按钮点击只播放一次点击音；
- 从控制台进入页面时，按钮音和页面打开音不重叠；
- 流程完成音只对配置的接收者播放一次；
- 离线重连、reload 或返回上一级不重播已经完成节点的声音。

记录测试时的窗口尺寸、GUI 缩放和资源包状态。任一分辨率溢出都应截图，不要只写“UI 有问题”。

## 16. 32/64 人性能

### 16.1 可重复的 UI 压力步骤

1. A 打开“开发与诊断”中的 64 人玩家档案/名单压力预览。
2. 先选择 32 人上下文。
3. 连续执行一次：打开 → 等待 10 秒 → 从顶部滚到底部 → 搜索/筛选 → 返回。
4. 切换 64 人上下文，重复同一序列。
5. 在 Compact、Standard、Wide 至少各做一次 64 人滚动。
6. 打开目标选择页面，检查虚拟化行复用时头像、名字、身份和选中状态不串行。
7. 返回控制台并再次进入，确认没有重复控件、持续音效或越来越慢的累积现象。

记录：

- 打开前后的 FPS 或帧时间；
- 首次打开耗时体感；
- 滚动是否卡死、跳行或丢失选择；
- 是否生成崩溃报告；
- 日志是否出现布局、Repeat、空 definition 或资源异常。

通过底线：

- 32 人和 64 人均能完成整套操作；
- 不崩溃、不冻结、不越界；
- 虚拟化只渲染可见范围，滚动后数据对应正确；
- 关闭页面后没有继续增长的声音、网络刷新或 UI 订阅。

### 16.2 权威运行时规模

自动自检应覆盖 0、1、32、64 人名单和 65 人拒绝。若另行使用真实账号或受控测试机器人连接 32/64 人，应单独记录工具、UUID 数、服务端 tick 和网络环境；没有真实连接时只填写“自动模型 + UI 模拟通过/失败”，不要写“真实 64 人服务器通过”。

## 17. 建议测试顺序

为减少世界状态互相污染，建议按以下顺序执行：

1. 新世界、握手和主持人认领；
2. 通用 `if_incomplete`；
3. 猎人 `always` 与身份延后提交；
4. 补员、移除和取消；
5. 离线与重连；
6. 正常停服与重启；
7. `/reload` 冻结；
8. 令牌透明续期、双击和旧上下文；
9. 回调失败与重试；
10. 资源错误；
11. BossBar、UI、声音和 32/64 人压力；
12. 最后执行 `immediate` 旁观者。

复杂异常测试前可复制一次完整世界作为检查点。不要依赖 `/reload` 清进度；它按设计不会清除游戏数据。
