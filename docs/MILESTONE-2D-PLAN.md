## 3. 已确认的产品决策

### 3.1 单活动任务

- 一个游戏同时只有一个任务或赛前环节；
- 状态顺序为“赛前环节/任务启动 → 进行中 → 结算 → 间隔 → 下一任务 → 时间线完成”；
- 路线是有限有向无环图，不允许循环；
- 不允许跳过任务，也不注册 `skipped` 结果绕过任务；
- 允许紧急终止整局，当前任务记为 `interrupted` 审计状态，不伪装成正常结果；
- 世界中已有已完成游戏数据时，不能自动覆盖或直接开始第二局。

### 3.2 时间

- 使用有效服务器 Tick，`20 Tick = 1 秒`；
- 服务器关闭、重启或崩溃期间不流逝；
- `/reload` 不暂停；
- 主持人主动暂停期间不流逝；
- 主持人掉线是否暂停由游戏定义配置，默认不暂停；
- 同时维护当前环节时间和正式游戏时间；
- 每个任务和间隔分别声明是否计入正式游戏时间；
- 赛前热身通常不计入正式游戏时间。

### 3.3 完成与结果

任务支持：

| 策略 | 语义 |
|---|---|
| `timeout_only` | 只能到时结算 |
| `early_or_timeout` | 可以提前提交，也可以到时结算 |
| `event_only` | 没有自动超时，只能由受控事件提交 |

- 每个任务最终只有一个全局结果 ID；
- 模组只接受第一次合法结果；
- 玩家个人奖励由数据包处理，不塞进全局结果模型；
- 到时先进入结算并调用 `on_timeout`；若数据包没有提交结果，停留在结算异常；
- 默认不允许主持人指定结果；
- 任务显式允许时，主持人只能在结算异常中选择已注册正常结果，且必须二次确认；
- 已冻结结果不能更换或覆盖。

### 3.4 间隔

- 结果可注册不同间隔；
- 间隔归零默认自动开始下一任务；
- 主持人可以暂停、继续、延长、提前结束间隔并开始下一任务；
- 延长和提前结束等改变时间线的操作必须二次确认；
- 最终结果可以进入可配置的最终间隔，随后自动转换到数据包注册的结束阶段。

### 3.5 可见性与回顾

- 主持人始终能看完整时间线、候选分支和诊断；
- 普通玩家默认没有实时任务时间线入口；
- 数据包可把未来任务标记为 `full`、`teaser` 或 `hidden`；
- 分支未决时只显示“由本次结算决定”和允许公开的候选，不公开结果到分支的映射；
- 结果冻结后才能公开确切下一任务；
- 玩家实时历史默认隐藏；
- 赛后回顾默认向本局参与者开放，从 ESC 菜单主动进入；
- 回顾只显示实际发生过的赛前环节和任务；
- 主持人能看技术审计，玩家不能看后台错误。

### 3.6 猎人出生点

- 出生点选择是通用 `exclusive_choice` 字段能力的首个用途；
- 数据包注册出生点 ID、名称、说明和预览；
- 玩家点击选项卡片时立即请求权威 `HOLD`，模组保证同一选项只能被一名玩家预约；
- 再次点击自己的 `HELD` 立即 `RELEASE`，点击另一选项由服务端原子改选；
- 普通释放不能删除 `LOCKED`，占用、释放、冲突和最终锁定都会广播给同流程页面；
- 临时预约允许在最终确认前更改；
- 最终确认页可以返回选择页重选，返回时保留当前 `HELD`；
- 完成流程后锁定；
- `/reload`、重启和掉线保留；
- 猎人身份移除时释放预约；
- 猎人重新初始化期间保留原预约，新流程完成时原子交换；
- 出生点数量不足时不能发起流程；
- 开局前所有猎人都必须拥有有效预约；
- 选择完成不传送，任务开始后的猎人箱刷新、传送和释放由数据包负责。

### 3.7 可见名称与 UI 标点

- 数据包注册没有外围括号的干净中文名称；
- `『名称』` 只表示正式注册名称，`「对象」` 只表示当前对象或当前选项；
- 标点由统一渲染 helper 添加，helper 必须幂等，不能重复包裹；
- 英文只作弱化衬托，内部注册 ID 只进入开发与诊断页面。

## 4. 明确不做

2D 不做：

- 正式任务内容、地图机关、任务文案或路线；
- 多个并行任务；
- 循环任务图；
- 任务跳过；
- 多局历史档案库；
- 玩家通用实时任务浏览器；
- 自动推断数据包结果；
- 自动传送任务参与者；
- 自动修改游戏模式、身份、队伍或生存状态；
- 猎人箱、猎人释放批次或刷新逻辑；
- 任意脚本、Java 表达式或客户端代码执行；
- 通用存档编辑器；
- 把出生点写成猎人专用枚举；
- 自动广播任务事件。

### 5.1 模组权威

模组负责：

- 当前时间线实例、任务实例与状态；
- Tick 时钟；
- 结果首次提交和路由冻结；
- 任务计划冻结快照；
- 事件去重与容量限制；
- 回调执行记录和失败阻塞；
- 回顾事实；
- 独占选择预约；
- 主持人权限、二次确认、审计和恢复。

### 5.2 数据包权威

数据包负责：

- 任务、结果、分支、间隔、页面和文案；
- 地图条件与计分板判断；
- 任务世界效果；
- 动画、音效、动态消息；
- 猎人箱刷新、出生点部署和释放；
- 玩家个人奖励；
- 何时调用受控结果、事件和状态接口。

### 5.3 必须始终成立

1. 同一活动游戏至多一个未完成时间线实例；
2. 同一时间线至多一个当前任务实例；
3. 同一任务至多冻结一个正常结果；
4. 冻结结果后，下一任务、间隔和阶段转换不可变；
5. 当前任务使用批准开局时的完整计划快照；
6. `/reload` 不清除或热替换当前实例；
7. 回调失败不能被当成成功；
8. 技术故障不能伪装成正常任务结果；
9. 事件记录有界；
10. 同一 `exclusive_choice` 选项在同一作用域至多一个有效持有者；
11. 已完成游戏不能在未重置时被新局覆盖；
12. 客户端不能成为时间、结果、预约或阶段的事实源。

## 7. 世界状态 Schema v3

Schema v3 将原有 v2 状态保存在 `core`，并在顶层增加：

```text
active_game_instance_id
timeline
exclusive_reservations
recovery_snapshots
```

任务历史、事件、统计和可回顾事实保存在 `timeline.task_history` 及其中的任务实例内，不另维护第二份 `timeline_history` 或 `recap` 事实源。

### 7.1 时间线实例

当前实现保存：

```text
instance_id
game_id
content_version
snapshot
status
resume_status
current_task
task_history
game_elapsed_ticks
paused
pause_reason
created_at_server_tick
started_at_server_tick
completed_at_server_tick
timeline_revision
callback_ledger
```

当前阶段继续由 `core.active_phase_id` 保存；时间线路由通过持久的阶段转换触发器执行 `on_exit → on_enter`，而不是在时间线里复制一个可能分叉的阶段字段。

`state` 至少包括：

```text
pre_start
starting
running
settling
intermission
completed
interrupted
blocked
```

其中 `blocked` 是技术阻塞覆盖状态，必须同时保留原业务位置，恢复后回到原位置继续。

### 7.2 任务实例

当前实现保存：

```text
task_instance_id
task_id
kind
status
resume_status
elapsed_ticks
result
intermission
participants
started_at_game_tick
settled_at_game_tick
callback_ledger
lifecycle_callback_trigger
phase_transition_trigger
events
statistics
```

冻结 `result` 内包含结果 ID、下一任务或结束阶段、可选阶段转换、转换时机和冻结 Tick；路由不再在实例中保存第二份可变副本。

任务业务状态：

```text
starting
running
settling
settled
interrupted
blocked
```

### 7.3 迁移

- v1/v2 → v3 不得凭旧 `GamePhase` 推断已运行任务；
- v1 只有保守安全状态可自动迁移；无法证明安全的旧活动阶段进入迁移阻塞；
- 没有 2D 时间线数据的世界迁移为空时间线；
- 2C 的主持人、玩家、强制流程和完成历史原样保留；
- 迁移前创建恢复备份；
- 迁移失败保留原文件并阻止写回；
- 迁移不自动启动任务。

## 8. 动态阶段与 TAB 清理

### 8.1 阶段

- 服务端、网络快照和客户端页面统一使用完整数据包阶段 ID；
- `GamePhase` 只允许存在于旧存档解码边界；

- 新业务逻辑、排序、按钮可见性和页面文案不能再 `switch GamePhase`；
- 未注册或已删除的当前阶段进入诊断阻塞，不回退到猜测值。

### 8.2 TAB

身份、队伍和生存状态可注册：

- 前缀；
- 名称颜色；
- 排序优先级；
- 是否覆盖前一层前缀；
- 是否覆盖前一层颜色；
- 未初始化时是否公开。

合成顺序为：

1. role 基础样式；
2. team 补充或覆盖；
3. life state 补充或覆盖；
4. 主持人系统样式最终覆盖。

主持人始终使用金色 `[主持人]` 并排在最上。普通身份只有本次身份提交带有匹配的初始化流程 ID、版本和成功实例凭据后才公开；更早的历史完成记录不能绕过一次要求 `always` 的重新初始化。无初始化流程的身份立即公开。未公开身份不加前缀、不改颜色，也不应打乱初始自然排序。

第一套正式数据包推荐排序为主持人、猎人、逃走者、旁观者，但 Java 不识别这些名称。

## 9. 任务注册与冻结 DAG

数据包在 `tasks/` 注册独立任务，游戏定义的 `task_timeline.initial_task` 指定入口。从入口沿所有结果路由可达的任务构成本局计划。

批准开局前必须验证：

- 所有引用存在且同属活动游戏；
- 图非空、有限、无环；
- 所有正常结果有且只有一个去向；
- 路由最终到达 `end_phase`；
- 不能注册 `skipped`；
- 时长与间隔在上限内；
- 回调存在；
- 事件和统计 ID 唯一；
- 玩家可见性不会泄露隐藏分支；
- 所有开局前要求满足；
- 所有需要出生点的猎人有有效锁定预约。

当前 2D 不提供开局倒计时配置；主持人完成二次确认时，一个持久事务原子完成：

1. 重新验证批准资格；
2. 冻结完整可达计划；
3. 固定本局参与者；
4. 创建时间线实例；
5. 转换到注册的游戏阶段；
6. 启动首个赛前环节或任务。

任一步失败则全部不提交。

## 10. 任务状态机

正常链路：

```text
不存在
  → starting
  → running
  → settling
  → settled
  → intermission
  → 下一任务 starting
```

最终任务：

```text
settled
  → 可选最终 intermission
  → timeline completed
  → end_phase
```

约束：

- `on_start` 成功后才进入 `running` 并开始当前环节计时；
- `on_start` 失败时保持 `starting + blocked`；
- `running` 只能由合法结果提交、到时或紧急终止离开；
- 进入 `settling` 后停止当前任务计时；
- 结果及其路由冻结后才执行结算回调；
- 结算回调失败时不能进入间隔；
- 间隔结束前不能启动下一任务；
- 主持人暂停是覆盖状态，不制造新任务状态。

## 11. 双 Tick 时钟

### 11.1 当前环节时钟

- 任务 `running` 时递增任务 Tick；
- 间隔运行时递增间隔 Tick；
- `starting`、`settling`、`blocked` 和暂停时不递增；
- 任务实例切换时归零。

### 11.2 正式游戏时钟

- 只在时间线已经开始且当前环节 `counts_toward_game_time=true` 时递增；
- 数据包可以让热身、特定任务或间隔不计时；
- 暂停和服务器不运行期间不递增；
- 不因 `/reload` 归零。

### 11.3 时钟显示

网络只同步服务端基准值、状态和基准服务器 Tick。客户端可以在两次快照间平滑显示，但每次同步必须校正，不能向服务端回写。

## 12. 结果、结算与间隔

### 12.1 结果提交

受控结果提交至少携带：

```text
timeline_instance_id
task_instance_id
task_id
result_id
```

服务端验证：

- 活动实例匹配；
- 当前任务匹配；
- 当前状态允许；
- 结果已在冻结任务中注册；
- 完成策略允许当前时刻提交；
- 尚未冻结结果；
- 调用来源和权限合法。

第一次合法提交原子写入结果、路由、间隔和阶段转换。重复提交同一结果返回幂等成功或“已接受”；不同结果返回明确拒绝，不能覆盖。

### 12.2 到时

`timeout_only` 和 `early_or_timeout` 到时后：

1. 停止任务时钟；
2. 进入 `settling`；
3. 执行一次 `on_timeout`；
4. 等待数据包提交已注册结果。

数据包未提交、提交非法结果或回调失败时进入结算异常。模组不能猜测胜负。

### 12.3 结算

冻结结果后按顺序：

1. 记录结果和回顾事实；
2. 执行结果 `on_apply`；
3. 执行结果逐玩家回调；
4. 执行任务 `on_settled`；
5. 全部成功后进入间隔或结束阶段。

每一步写入独立最多一次记录。失败后主持人可重试未成功步骤，不能重跑已成功步骤，也不能更换结果。

## 13. 回调与技术故障

### 13.1 回调上下文

全局回调至少提供：

```text
game_id
timeline_instance_id
task_id
task_instance_id
result_id
game_elapsed_ticks
task_elapsed_ticks
```

逐玩家回调增加：

```text
player_uuid
player_name
player_field.<binding_name>
```

逐玩家回调以对应玩家作为命令源，字段只允许从定义中显式绑定。客户端不能提供宏值。

### 13.2 执行顺序

- 全局 `on_start` 先执行；
- `on_start_players` 后执行；
- 每名玩家独立记录成功；
- 任一必需回调失败则阻塞推进；
- 重试只执行失败或未执行项。

猎人部署的典型顺序是：全局回调构建猎人箱，再按冻结受众为每名猎人执行带出生点字段的部署回调。

### 13.3 幂等要求

数据包回调必须尽量幂等。模组保证逻辑上的最多一次成功记录，但无法撤销命令函数在异常中途已产生的世界副作用；诊断必须显示函数 ID、玩家、步骤和失败原因。

## 14. 任务事件与统计

### 14.1 事件

任务可注册事件，例如箱子封锁、认证完成或复活装置触发。每条记录包含：

- 任务实例；
- 事件 ID 和冻结显示名；
- 触发玩家 UUID 与当时名字，或系统来源；
- 正式游戏 Tick；
- 当前任务 Tick；
- 发生时任务状态；
- 可见性；
- 持久列表中的稳定发生顺序。

策略：

| 策略 | 约束 |
|---|---|
| `once` | 每任务实例最多一次 |
| `per_player` | 每任务实例每玩家最多一次 |
| `repeatable` | 必须声明有限 `max_records` |

2D 不自动播放消息、动画或声音。数据包在提交事件前后自行处理现场演出。

### 14.2 统计

统计定义只声明回顾需要冻结的事实：

- 计数；
- 时长；
- 布尔值；
- 文本或注册枚举；
- 玩家引用。

统计由数据包通过受控接口写入，服务端验证类型、任务实例和容量。统计不是结果路由条件，不能反向改写结果。

## 15. 赛后回顾

回顾在时间线创建时初始化，在游戏完成或紧急终止后可读，并一直保留到显式重置。

参与者页面显示：

- 实际发生过的赛前环节和任务；
- 开始、结束和持续时间；
- 公开结果；
- 可公开事件；
- 可公开统计；
- 事件在正式游戏第几分钟、当前任务第几分钟发生；
- 触发玩家的 UUID 与冻结名字；客户端用该 UUID 渲染真实皮肤基础层和帽子层，离线时对同一头像做灰度处理。

主持人额外看到：

- 完整候选路线和参与者；
- 回调记录、技术阻塞和重试；
- 当前时间线实例、revision 与审计摘要；
- 通过高风险操作确认链留下的人工干预审计。

回顾不展示未走到的分支、隐藏后台错误或无关世界历史。

## 16. 独占选择与猎人出生点

### 16.1 通用模型

`exclusive_choice` 是玩家持久字段类型。预约键为：

```text
game_id + field_id + scope_id + option_value
```

第一版 `scope_id` 使用当前活动游戏实例。一个选项最多一个有效预约，一个玩家对同一字段最多一个有效值。

字段、选项、名称、说明、图标、页面布局和业务用途全部来自数据包。模组只实现通用独占事务，不写死猎人出生点、任何具体点位或地图语义。

### 16.2 预约状态

```text
available
held
locked
```

- 进入选择页不自动占用，点击卡片时立即向服务端请求 `HOLD`；
- 再次点击自己的 `HELD` 时立即请求 `RELEASE`；
- 改选时服务端原子释放旧临时值并占用新值；
- 普通 `RELEASE` 不能删除 `LOCKED`；
- 流程最终完成时转为 `locked`；
- 占用、释放、冲突、原子改选和最终锁定后，服务端向仍在同流程中的相关页面广播最新状态；
- `confirm` 节点可选声明 `back` 返回选择节点，返回时保留当前 `HELD`；
- 掉线、重启和 `/reload` 保留；
- 放弃或取消未完成新流程时释放本次临时预约。

### 16.3 重新初始化

猎人已经拥有锁定出生点时：

- 旧预约继续有效；
- 新流程使用独立候选预约；
- 完成时原子释放旧值并锁定新值；
- 新流程取消、失败或超时时保留旧值；
- 同一选项不能因“旧值属于自己”以外的情况被重复占用。

### 16.4 身份联动

- 数据包在身份定义中声明出生点字段为开局要求；
- 新增猎人后，该玩家在满足要求前阻止开局；
- 猎人改为其他身份后释放该身份绑定的预约；
- 主持人可二次确认允许单名猎人重新选择；
- 主持人不能手工制造重复预约。

### 16.5 出生点与释放状态分离

- 出生点只表示开局部署选择，不表示猎人已经释放；
- 等待释放、已释放和释放批次使用数据包注册的身份、队伍、生存状态、持久字段或标签组合表达；
- 任务结果通过受控状态变更和数据包回调完成释放；
- 模组不理解猎人箱、批次或释放条件的具体含义。

## 17. 主持人控制台

控制台随当前状态优先显示：

### 开局前

- 未满足的开局要求；
- 未选择出生点的猎人；
- 活动流程成员行显示“尚未选择 / 临时预约：中文选项名 / 最终锁定：中文选项名”的权威摘要；
- 任务计划摘要；
- 批准开局。

### 任务进行中

- 当前任务、双时钟和参与人数；
- 最近公开事件；
- 暂停；
- 紧急终止；
- 完整时间线入口。

### 结算异常

- 失败步骤和数据包函数；
- 重试；
- 任务显式允许时的人工结果；
- 紧急终止。

### 间隔

- 下一任务；
- 剩余时间；
- 暂停/继续；
- 延长；
- 提前开始下一任务。

### 游戏结束

- 赛后回顾；
- 重置本局进程；
- 清空 Pixel TZZ 全部数据。

所有页面沿用 2B/2C 的深蓝、金、青、深红视觉基线；右上角只显示一份共享同步徽标。玩家头像必须绘制真实皮肤基础层和帽子层，离线时对同一头像做灰度处理。

## 18. Reset、Reload 与 Restart

### 18.1 `/reload`

- 解析并验证新定义；
- 新定义只用于下一次显式重置后的运行；
- 当前时间线继续使用冻结快照；
- 当前任务和 Tick 不暂停；
- 不清事件、回顾、结果或预约；
- 新定义错误时禁止依赖新定义的新操作，但不破坏当前持久状态。

### 18.2 正常重启

- 保存当前业务状态和 Tick；
- 停机时间不计时；
- 恢复当前任务、结算、间隔、阻塞、事件和预约；
- 不重复成功回调；
- 客户端重新同步后显示相同状态。

### 18.3 两级重置

`重置本局进程`：

- 保留活动游戏与主持人；
- 将玩家身份与生存状态恢复为游戏默认值，并清除初始化凭据、队伍、字段、准备、强制流程、时间线、任务、事件、回顾和预约；
- 返回活动游戏的初始阶段。

`清空 Pixel TZZ 全部数据`：

- 清除主持人、活动游戏和全部 Pixel TZZ 持久状态；
- 回到未认领、未选择游戏状态。

两项都必须二次确认、写明清除范围、使用一次性服务端授权并写入审计。`/reload` 永不触发重置。

## 19. 网络、安全与性能

### 19.1 网络

- 2D 当前协议为 v10；相对 v9 的扩展是 `exclusive_choice` 卡片点击后的即时权威预约 mutation；
- 客户端只请求动作，不提交权威时钟或结果；
- 所有动作带实例 ID 与 revision；
- 旧页面、旧实例和重复请求明确拒绝；
- 页面可先打开骨架，再在原页面内同步内容；
- 同步等待只显示中性加载状态，不闪红色错误；
- 请求期间其他控件不得重建或闪烁。

### 19.2 安全

- 数据包结果和事件接口只允许服务端命令源；
- 玩家客户端不能直接触发结果；
- 主持人操作每次服务端重新验证；
- 人工结果、紧急终止、重置、延长和提前开始都需要二次确认；
- 回调宏严格转义，只暴露声明字段；
- 资源 ID、玩家、任务实例、结果、事件和统计都做边界校验。

### 19.3 容量

当前实现已经给出明确常量并要求自动检查覆盖，至少限制：

- 每游戏任务数；
- 每任务结果数；
- DAG 总边数；
- 每任务事件定义数；
- `repeatable` 事件记录数；
- 每任务统计数；
- 回顾总记录数；
- 回调字段绑定数；
- 独占选项数；
- 快照序列化大小；
- 网络页大小。

达到上限时拒绝新记录并诊断，不能无限增长或静默删除已冻结回顾。
