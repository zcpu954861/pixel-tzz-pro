## 1. 使用方式

本手册供 V3C 实现收口后的逐项五客户端验收。原 archived 分支中的常驻 HUD、右下角信息坞、
组件路由和布局设置不属于本轮测试。

验收节奏：

1. 主代理一次只给用户一项测试；
2. 必要的 `/reload`、函数和预期结果在同一条消息一次说全；
3. 用户回复 `PASS` 或提供截图、客户端、现象和顺序；
4. 一轮发现的问题全部记录，用户明确结束该轮后集中修复；
5. 修复后只回归受影响项及必要前置项；
6. 自动检查、日志无异常和客户端成功启动不能替代真实画面、声音与多人同步；
7. 没有用户明确反馈的项目始终保持“待实机”；
8. 全部问题通过前不提交、不推送、不合并。

失败时至少记录：

- 项目编号与客户端；
- 分辨率、GUI Scale、FPS、F1/TAB/聊天/ESC 状态；
- 操作前后画面和触发命令；
- 是否首次进入、Reload、重连或重启恢复；
- countdown instance、purpose、state、remaining 和 state version；
- `logs/latest.log` 对应时间附近首个异常；
- 是否稳定复现、其他客户端是否同时发生。

## 2. 自动检查与实机边界

### 2.1 实机前自动门

目标专项任务：

```powershell
.\gradlew.bat countdownDefinitionSelfCheck
.\gradlew.bat countdownAuthoritySelfCheck
.\gradlew.bat countdownRestrictionSelfCheck
.\gradlew.bat countdownPersistenceSelfCheck
.\gradlew.bat countdownCallbackLedgerSelfCheck
.\gradlew.bat countdownCallbackRetryConfirmationSelfCheck
.\gradlew.bat protocolV13SelfCheck
.\gradlew.bat settingsUiContractSelfCheck
.\gradlew.bat clean check build --console=plain --no-daemon
git diff --check
```

任务名必须以最终 `build.gradle` 实际注册结果为准；若实现采用不同稳定名称，应同步本文，不得
让文档长期列出不存在的任务。

### 2.2 自动检查应证明

- Countdown 严格 JSON、覆盖、错误隔离与上一代恢复；
- Game opening 引用、required/optional 与旧 API 兼容；
- 全局单实例，不覆盖、不排队；
- 状态机、掉线、限制、取消、LaunchPlan 和 callback ledger；
- Schema v5 持久化、迁移和 recovery wait；
- v13 Replace/Patch/Clear、乱序、tombstone 与 Resync；
- seconds/tenths/hundredths 格式和固定宽度；
- 逐位差异、借位、暂停落位和低 FPS 追帧纯逻辑；
- 本地设置不能隐藏、扩大受众或修改权威时钟；
- 无 Countdown 的 2D 立即开局路径。

### 2.3 自动检查不能证明

- ActionBar 上方的位置是否自然；
- 字体、背景、描边、间距和进度线是否达到 3A 质量；
- 逐位滚动是否顺滑、不抖、不闪；
- `0.01s` 在真实 60/144 FPS 下是否可读；
- 五端关键秒、声音和完成是否一致；
- ESC、F1、聊天、窗口缩放和原版 ActionBar 共存是否正确；
- 取消、掉线、正常重启和限制解除的实际手感。

### 2.4 修复回归的证据边界

本轮集中修复使用以下三类证据，不能互相替代：

| 类型 | 本轮由它证明 | 不能由它证明 |
|---|---|---|
| 自动门决定 | 严格解析、诊断数量上限、`READY_WITH_WARNINGS`、上一代 Canonical/SHA 保留、新 generation 依赖闭包复核、旧确认令牌拒绝、32/64 人纯逻辑、乱序与墓碑 | 主持人是否真的看见中文警告、按钮是否好点、动画和声音是否自然 |
| 单客户端实机 | 主持人卡片文案、`01:02 → 01:01` 首次滚动、四态本地预览、确认页排版 | 非主持人是否泄漏、五端同步、掉线恢复、独立音量 |
| 多客户端实机 | 主持人与普通玩家诊断隔离、快捷操作对真实状态的影响、独立音量、暂停/重连/继续、取消与清空后的全端解除、受众与同步 | 64 人完整容量、每个账本分支和全部乱序组合 |

其中“自动门决定”的项目不要求用五个真实账号穷举；“多人实机”的项目即使已有纯逻辑自检，
也必须取得用户对真实 UI、声音或同步结果的明确反馈。任何“已修”只表示代码或数据包改动已经
落地，未取得反馈前统一写作“**已修，待实机回归**”。

## 3. 环境与固定分工

### 3.1 世界

可复用 3A/V3B 验收世界副本，不需要新地形。首次安装前备份，再安装最新
`examples/pixel-tzz-base-datapack`。

不要用 `/reload` 清数据。`/reload` 只重载资源并保留活动实例；清空时使用主持人控制台明确的
“重置本局进程”或“清空 Pixel TZZ 全部数据”，审阅目标、影响和不可恢复内容。

原 archived HUD 数据不应进入新验收世界。若从旧 3C 原型世界迁移，必须先验证迁移不会残留
信息坞、HUD 偏好、路由或屏幕 Overlay。

### 3.2 五客户端

| 客户端 | 固定用途 |
|---|---|
| Player972 | 主持人、命令执行、取消、Reload 与恢复 |
| PlayerB | 猎人、掉线和完整动画 |
| PlayerC | 逃走者、低 FPS、重连和百分位 |
| PlayerD | 逃走者、默认设置对照 |
| PlayerE | 逃走者、静态、高对比与静音对照 |

批量启动：

```powershell
.\start-test-clients.cmd
```

按 Player972、B、C、D、E 顺序启动。单独重启某客户端时继续复用其独立实例目录，不能复制
其他玩家 UUID 或偏好。

### 3.3 目标验收夹具

实现应提供等价的受控入口，最终名称与示例数据包一致：

```text
pixel_tzz:acceptance_3c/setup
pixel_tzz:acceptance_3c/clear
pixel_tzz:acceptance_3c/countdown/start
pixel_tzz:acceptance_3c/countdown/player_loss_pause
pixel_tzz:acceptance_3c/countdown/player_loss_cancel
pixel_tzz:acceptance_3c/countdown/player_loss_continue
pixel_tzz:acceptance_3c/countdown/callback_fault
pixel_tzz:acceptance_3c/countdown/callback_fault_clear
pixel_tzz:acceptance_3c/countdown/recovery
```

三档时间精度与数字动画由三份真实定义直接覆盖，不另造只为测试存在的函数：

- `pixel_tzz:opening/pause`：`seconds + hundredths`、逐位 `roll`，并启用小数位动画；
- `pixel_tzz:opening/cancel`：`mm_ss + seconds`、`instant`；
- `pixel_tzz:opening/continue`：`seconds + tenths`、逐位 `roll`，小数位直接更新。

当前 Game 默认引用 `pixel_tzz:opening/pause`。`player_loss_*` 函数只写入验收提示和预期记录，
不会绕过资源加载去改写 Game。验收另两份定义时，应在新一轮批准前修改
`games/main.json` 的 `opening_countdown.definition`，执行一次 `/reload`，再从正式主持人入口批准。
活动实例继续使用批准时冻结的旧定义。

夹具只能准备数据或调用正式受控入口，不能绕过 authority 直接向客户端发伪造包、强行修改
remaining 或调用内部 opening complete handler。

### 3.4 集中修复后的单项回归顺序

恢复测试时严格按下列顺序，一次只发一项操作和一组预期；前一项没有结论前不启动后一项：

1. **R1 / 3C-02A**：未知字段；确认主持人看到中文字段诊断，普通玩家无路径和异常栈。
2. **R2 / 3C-04A**：从没有历史版本的 required 缺失定义启动；确认仍阻断，并显示原因和 `/reload`
   恢复指引。
3. **R3 / 3C-10B**：先加载合法紫黑样式，再把同一被引用定义改为 `max_width: 999`；确认显示
   “有配置警告”、继续使用上一代样式且开局按钮仍在，修正后警告只清除一次。
4. **R4 / 3C-04 快捷操作**：在等待批准状态确认“启动/无倒计时降级”进入快捷区；后续只核对
   当前确实适用的取消、回调重试或交接操作，不能为了凑按钮伪造状态。
5. **R5 / 3C-12**：单独运行 62 秒定义，只观察首次 `01:02 → 01:01`，确认逐位滚动已恢复。
6. **R6 / 3C-22**：单独循环 RUNNING → PAUSED → WAITING → COMPLETED 本地预览，并用另一客户端
   确认没有预览投影或声音泄漏。
7. **R7 / 3C-21**：默认音量、静音端和 V3B 字符音量对照；验证新的原版 Checkpoint 音阶、节点
   去重与 Reload/Resync 不补播。
8. **R8 / 3C-16**：required player 掉线并以同一 UUID 返回；确认准备仍为 `4/4`、不再弹准备页，
   倒计时从冻结值继续。
9. **R9 / 3C-25**：正常取消、状态变化后重新审阅、令牌过期三轮分开执行；确认每轮都有二次确认
   和明确结果。
10. **R10 / 恢复兜底**：另起一轮活动 Countdown，确认“清空全部数据”仍可审阅；只在明确接受
    清除整局数据后执行，并确认全端 Countdown、限制和强制页一起退出。
11. **R11 / 3C-18、3C-19**：补完三档模式在同一权威实例中的完成同步，以及低 Alpha/近似色的
    高对比保护。
12. 上述定向回归全部通过后，才按 **3C-23 → 3C-35** 的原顺序继续未测项目。

R1、R2、R3、R4、R6、R7、R8、R9、R10 都包含权限、受众或全端状态，必须至少同时观察主持人
和一名普通玩家；R5 可单端判定视觉，但不得据此替代后续五端完成同步。R10 是破坏性恢复验证，
必须独立于 R8/R9，不能用它顺手清场后把多个项目一起判定。

- 普通玩家不看到路径和异常栈；
- 失败时保留上一代有效定义；
- 修复后只发布一次，不重建活动实例。

实机记录（2026-08-05）：

- 3C-02A 未知字段：**FAIL**。坏 Countdown 被隔离，主游戏定义继续可用，五端未因协议或
  Reload 断开；但主持人控制台仍显示“内容定义 已就绪”，只把总数从 `100` 增为 `101`，没有
  任何有界中文错误诊断，主持人无法得知被禁用定义及原因。其余坏输入变体留到该诊断投影修复后
  一次性定向回归，不重复验证同一缺陷。
- 测试夹具附带发现：`pixel_tzz:acceptance_3c/clear` 因整条 Storage 清理命令语法不完整而未能
  加载；已改为分别清理 `setup` 与 `countdown` 根路径，待 R1 随 Reload 一并回归。

集中修复（2026-08-05，**已修，待实机回归**）：

- Countdown 局部失败不再伪装成完全正常的 `READY`；发布状态为 `READY_WITH_WARNINGS`，核心
  generation 保持健康。主持人获得有界中文 ID、字段、原因和 `/reload` 指引，普通玩家仍只得到
  通用健康信息。
- 当前 Game 引用的新 Countdown 缺失或无效时，会先在新 generation 下重新核验上一代定义的
  Callback、Checkpoint Cue 与投影预算；闭包仍安全才保留上一代 Canonical/SHA。新错误诊断与旧
  可执行定义同时保留，但按同一 ID 只计一项。没有安全旧版本时，required 仍保持阻断。
- 修正后的合法定义应替换回退版本，并清除 warning、disabled 与 retained-fallback 标记。上述
  原子性、诊断上限和闭包失效分支由专项自动检查覆盖；真实主持人文案及普通玩家不泄漏仍按
  R1–R3 实机确认。

  因此尚无证据表明 V3C 重新放行了已删除的猎人 Subtitle；基础验收包仍有通用初始化、阶段、游戏
  和任务自行注册的合法 Hook。为避免误删数据包能力，本轮不凭推测移除这些 Hook；定向复测必须
  记录实际 Subtitle 文案，再按该文案对应的注册源处理。

## 5. B 组：固定位置与视觉质量

### 3C-26 required player 的 pause / cancel / continue
